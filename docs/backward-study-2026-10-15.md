# Обратный проход по весам: результаты блока 15–16 октября 2026

Рабочий отчёт TASK-21. Блок начат в 17:35 UTC по поручению работать 2,5–3 часа.
Mac M1 используется для разработки и CPU-проверок; все CUDA-измерения — Windows
RTX 4070 Ti, Torch 2.1.0+cu118. Зависимости не обновляются.

**Основная матрица завершена:** 24 обучения в 12 парах прошли все заранее
заданные критерии. Принят `training.backward: auto`: `parameters` для точных
условий Робина/Неймана на одном CPU/CUDA с FP32, `all` в остальных случаях.
Раскрытое продолжение остаётся дополнительной опцией; его прежний отдельный
критерий качества не выполнен. Оставшиеся проверки перечислены в конце отчёта.

## Что изменилось

Конечный обратный проход передаёт PyTorch только обучаемые веса как целевые
листья графа. Внутри PDE координатные производные остаются полностью.
Один метод `PINNModule.backward` используется и автоматическим циклом Adam
в Lightning, и функцией L-BFGS. Сохранены обычные события Lightning, обнуление
градиентов, фиксированная цель при поиске шага и счётчики вычислений.

Режим не меняет физическую сигнатуру сохранённой модели. Его можно переключать
при предсказании или новом обучении из весов. Начальная поддержка ограничена
одним CPU/CUDA и `32-true`; смешанная точность, MPS и несколько устройств
отклоняются явно. Обоснование:
[parameter-backward.md](parameter-backward.md),
[подробный математический разбор](parameter-backward-math.md).

Дополнительно обобщён измеритель срезов обучения: вместо зашитой задачи
Дирихле 3D он принимает тепловые задачи разной размерности, способы точных
преобразований и режимы обратного прохода. Подготовка плана, обучение со
срезами и независимая оценка разделены на небольшие объекты.

## Почему это сохраняет уравнение

Для заданных координат X оптимизатору нужен градиент по весам θ:

$$
\nabla_\theta\mathcal L(\theta;X),\qquad
\mathcal L=\frac{1}{n}\sum_k
\left[u_t-\kappa\Delta u-f\right]^2(X_k).
$$

Дополнительный конечный градиент функционала по X не используется, поскольку
оптимизатор не перемещает точки. Внутренние производные температуры по X
сохраняются. Точный фон b входит в полную невязку, но при линейном тепловом
операторе его вклад не зависит от весов:

$$
r=\mathscr Lb(X)+\mathscr Lc_\theta(X)-f(X),\qquad
\partial_\theta r=\partial_\theta\mathscr Lc_\theta(X).
$$

Нельзя выбросить фон из самой невязки: он остаётся множителем в градиенте
квадрата ошибки. Выбираются только конечные цели дифференцирования.

## Неожиданность: первый вызов не совпал с повтором

Первоначальная проверка точного равенства остановила очередь на расхождении
1,80·10⁻⁸. При отдельной диагностике сам холодный контроль `all` отличался от
повторного `all` до 1,36·10⁻⁷ (относительная норма 1,59·10⁻⁵).
Последующие повторы и сравнения режимов совпали. Конкретная внутренняя причина
в CUDA не установлена; исходные измерения сохранены, результат не скрыт.

Исправление измерителя — одинаковый прогрев обоих режимов и отдельная проверка
самоповторяемости, а не ослабление допуска. Критерий точного равенства
прогретых градиентов и пороги качества решений сохранены.

Бенчмарки оставляют контроль `all` по умолчанию; это отдельная настройка
от автоматической политики пользовательского решателя.

Важно различать ошибку температуры на границе и невязку граничного оператора.

не является ошибкой выполнения условия Неймана. Строгая проверка использует
`boundary_operator_rmse` и независимый тепловой баланс.

## Время достижения точности

Новый измеритель сохраняет промежуточные веса без доступа к аналитическому
ответу. Ошибки считаются только после завершения всех шагов конкретного опыта.
Для подтверждения нужны два соседних успешных среза; если сразу после Adam
порог уже выполнен, время до него неизвестно и отмечается `left_censored`.
Между срезами возможны незамеченные пересечения: это первое наблюдаемое
подтверждённое достижение, а не доказанная точка непрерывной траектории.

Подготовка, обучение со срезами, запись срезов, независимая оценка и тёплое
предсказание учитываются отдельно. Текущий протокол и ограничения:
[time-to-quality-screening.md](time-to-quality-screening.md).

### Основные четыре опыта со срезами

Код `e307575`, сначала два режима seed 19, затем обратный порядок seed 1234
в том же Python-процессе. Пороги: общая относительная ошибка ≤0,001,
последняя ≤0,002, независимая PDE-невязка ≤0,015 одновременно.

| Состояние | Режим | Предыдущий неуспех, с | Первый успешный срез, с | Подтверждение, с |
|---:|---|---:|---:|---:|
| 19 | all | 337,15 | 352,77 | нет |
| 19 | parameters | 283,44 | 295,89 | нет |
| 1234 | all | 320,37 | 335,87 | 351,66 |
| 1234 | parameters | 255,97 | 268,30 | 280,86 |

Для seed 1234 метрики всех срезов совпали точно; верхнее наблюдаемое время
меньше примерно на 20,1%. Интервалы соседних наблюдений разнесены, но это
только одна подтверждённая пара, не пятисостоянийная приёмка времени до порога.
Для seed 19 прошёл лишь последний срез, поэтому подтверждения нет у обоих
режимов. На шаге 100 контрольная PDE-невязка **0,0150012206**, чуть выше 0,015;
округление до 0,015 не превращает его в успех.

Запись пяти срезов заняла 5,45–6,85 мс, менее 0,003% обучения; независимая
оценка — 10,47–10,60 с и не входит во время срезов. Тёплое предсказание
0,627–0,635 с измерено **контрольным eager-оценщиком**, а не обучавшим
`robin_grouped`: его нельзя сравнивать с производственным временем 0,295 с
из основной матрицы. Входы уже на GPU; это не таймер полного файлового запуска.
[Исходные четыре опыта](experiments/2026-10-16-backward-convergence.json).

### Неожиданность: жизненный цикл процесса

У seed 19 в общем процессе обнаружены небольшие различия после Adam,
которые L-BFGS усилил: последняя относительная ошибка 0,000678496 у контроля
против 0,000730626 у кандидата. В основной матрице 12 пар **разных процессов**
совпали точно. Это различие нельзя скрывать за итоговым ускорением.
Конкретная причина внутри CUDA не установлена; ранее холодный вызов отличался
даже от повторного вызова того же контроля.

До диагностического повтора зафиксирован
[дополнительный протокол](experiments/2026-10-16-backward-isolation-protocol.json):
тот же seed 19, настройки и пороги, но новый Python-процесс на каждый режим.
Его результат рассматривается отдельно от основной пятисостоянийной приёмки.
Повтор не является полным исследованием самоповторяемости обоих режимов.

Диагностический повтор завершён: отдельные процессы дали **точно одинаковые
веса и метрики всех пяти срезов**, а итоговые веса обоих режимов совпали
с исходными моделями `f1bf7bb`. Контроль — 350,43 с, кандидат — 278,99 с,
снижение времени на 20,39%. Последний порог у seed 19 снова прошёл лишь
на последнем срезе: время достижения по прежнему правилу **не подтверждено**.

На CPU Windows сравнены 22 пары сохранений: все изолированные срезы,
контроль общего процесса с изолированным, итог с исходными моделями,
и пять срезов общей пары seed 1234. Различие осталось только у `parameters`
seed 19 в общем процессе: максимум разницы весов после Adam — 6,26·10⁻⁷,
после L-BFGS — 0,00506. Это согласуется с влиянием состояния процесса и
усилением малых отличий оптимизацией, но не устанавливает конкретную причину
в CUDA. Байты сериализации и история оптимизатора у срезов не сравнивались:
срезы содержат лишь значения состояния модели.

Для будущих сопоставлений одноразового runner принят способ запуска:
**один новый процесс на один вариант и состояние генератора**. Он уже
доступен обычным CLI: одно значение `--seeds` и одно значение `--backward`
на отдельный вызов `benchmark_time_to_quality.py`.
Изменения PDE или оптимизатора ради повторяемости не понадобились.
[Все результаты диагностического повтора](experiments/2026-10-16-backward-isolation.json).
Итого в блоке 30 полных численных обучений: 24 основных, 4 со срезами и
2 диагностических. Дополнительные опыты не подменяют исходную приёмку.

## Дополнительная проверка объяснения поздней ошибки

На Mac разобраны шесть **уже сохранённых** решений предыдущего опыта выборки,
без нового обучения/предсказания. Гипотеза о преимущественно медленных модах
поздней ошибки не подтвердилась для равномерной выборки: в дискретной системе
Неймана быстрые формы дают 54–84% энергии ошибки. У неудачной поздней плотности,
наоборот, 42–51% энергии находится в постоянной форме. Поэтому одна проекция
на исходную затухающую форму не описывает всё качество.

Первоначальные проценты относятся к грубой сетке и трапециевидному скалярному
произведению. После восстановления SSH вывод подтверждён на независимых
квадратурах Гаусса 13/17: быстрые формы 53,82–83,88%, постоянная при поздней
плотности 42,07–51,41%. Полная энергия последнего слоя между квадратурами
различается не более чем на 0,00215%. Это численная проверка сходимости,
не строгий непрерывный сертификат и не замена прежним метрикам.
Вывод, ограничения дискретизации и энергетическая оценка без полного эталона:
[neumann-error-spectrum.md](neumann-error-spectrum.md).

## Ограничение профилировщика Windows

Отдельная проверка установленного Torch2.1.0+cu118 вернула
`supported_activities = {ProfilerActivity.CPU}`. Трассы содержат CPU-события
операторов, но не события CUDA-ядер. При этом таблица имеет ненулевые CUDA-времена.
Такое сочетание соответствует резервному пути профилировщика:
[исходный код Torch2.1.0](https://github.com/pytorch/pytorch/blob/v2.1.0/torch/autograd/profiler.py#L243)
выбирает его при отсутствии CUDA в поддерживаемых активностях;
[документация профилировщика](https://docs.pytorch.org/docs/main/profiler)
объясняет наличие CUDA-времён в таблице без CUDA-событий в JSON.

Следовательно, отсутствие событий ядер или копирования **не означает**,
что запусков/переносов не было. Полное разложение по ядрам, перекрытию и
передачам на этом инструменте не получено. Счётчики `aten` нельзя выдавать
за число CUDA-ядер. Это остаётся ограничением TASK-21, а не пройденной проверкой.
Синхронизированные времена без профилировщика и измерения памяти получены
независимо и этим ограничением не отменяются. Никакие библиотеки/драйверы
в производственной среде ради профилирования не обновлялись.

## Настоящий перенос GPU-модели обнаружил ошибку метаданных

Проверка на реальном файле Windows выявила `WindowsPath` в служебных данных
ModelCheckpoint: обычный `torch.load` на Mac не мог восстановить такой путь.
Симуляция CUDA-конфига на Mac этого не обнаруживала. Исправлены запись каталога
строкой и локальное декодирование чужих путей как PurePath, без глобальной
подмены `pathlib` и без изменения тензоров. Публичные команды `predict` и `retrain` проверены.

Настоящая сохранённая CUDA-модель перенесена на Mac: все 22 599 значений публичного
CPU-предсказания отличаются от сохранённого GPU-результата не более 9,54·10⁻⁷.
Нового обучения не было. Полный CPU-набор после этого изменения — 498 пройдено,
255,75 с; Ruff/format/strict mypy — 92 файла. Последняя дополнительная проверка явных
позиционных аргументов backward выполнена отдельно: 10 пройдено.
Подробности: [checkpoint-portability.md](checkpoint-portability.md).

## Практические выводы

1. Конечный обратный проход можно удешевить, сохраняя физический оператор,
   все внутренние производные и бюджет оптимизатора. Основная матрица отдельных
   процессов подтвердила это на текущем стеке; численная повторяемость в другом
   жизненном цикле процесса проверяется отдельно.
2. Точное условие Неймана фиксирует производную, но не температуру на грани.
   Поэтому граничное значение температуры нельзя использовать вместо проверки
   граничного оператора. Тепловой баланс и независимая PDE-невязка обязательны.
3. Ошибка последнего слоя не сводится к одной исходной затухающей форме.
   Постоянная и быстрые формы требуют разной интерпретации. Просто сместить
   точки к концу времени оказалось неудачной стратегией в прежнем опыте.
4. Явный запрос поля на последнем физическом времени из настоящего сохранения
   совпал с последним слоем MAT в пределах 9,54·10⁻⁷. В этом проверенном пути
   признаков сдвига индекса времени нет. Это не формальное доказательство
   отсутствия любой ошибки индексации во всём проекте.
5. Новый граничный базис может оказаться дешевле, но меняет конечную модель.
   Нужны контрпримеры и проверка производных: точность графика температуры
   сама по себе не означает маленькую невязку. Символьный пример двух
   полиномиальных признаков описан отдельно; действующий решатель не изменён.

## Как воспроизвести отдельную пару

Точные исходные настройки каждой модели лежат в сохранённом `config.resolved.yaml`,
а версия — в JSON опыта. Историческая матрица выполнена на `f1bf7bb`;
новый повтор на другой версии — отдельный опыт. Не объединять состояния
разных версий в одну сравнительную группу. Контроль и кандидат отличаются
только `backward`, остальные настройки и состояние генератора одинаковы.

Ниже содержимое PowerShell-команды для передачи через неинтерактивный SSH
с кодированием UTF-16LE, как описано в AGENTS.md. Первые две строки обязательны.
Пример повторяет одну пару Неймана 3D; при повторении выбрать новое имя каталога.
Для нечётных позиций списка состояний порядок режимов обращается.

```powershell
Set-Location -LiteralPath 'C:\Projects\pinn-runner' -ErrorAction Stop
if ((Get-Location).Path -ne 'C:\Projects\pinn-runner') { exit 1 }
$ErrorActionPreference = 'Stop'
$env:PYTHONDONTWRITEBYTECODE = '1'
$env:TEMP = 'C:\Projects\pinn-runner\.tmp'
$env:TMP = $env:TEMP
$env:CUDA_CACHE_PATH = $env:TEMP + '\cuda'
$env:MPLCONFIGDIR = $env:TEMP + '\matplotlib'
git rev-parse HEAD
if ($LASTEXITCODE -ne 0) { exit $LASTEXITCODE }
foreach ($mode in @('all', 'parameters')) {
    $out = 'numerical-reports/backward-reproduction-19-' + $mode + '-001'
    & '.\.venv\Scripts\python.exe' scripts/benchmark_solutions.py `
        --device cuda --profile standard --cases heat_neumann3d --seeds 19 `
        --steps 2000 --lbfgs-steps 150 --constraints hard_initial_robin `
        --hard-execution robin_grouped --hard-lifting recursive `
        --backward $mode --collocation-points 2048 --output-dir $out
    if ($LASTEXITCODE -ne 0) { exit $LASTEXITCODE }
    $trial = $out + '/heat_neumann3d-19'
    & '.\.venv\Scripts\python.exe' scripts/benchmark_robin_balance.py `
        --trial $trial --report ($trial + '/balance.json') --quadrature gauss_legendre
    if ($LASTEXITCODE -ne 0) { exit $LASTEXITCODE }
    & '.\.venv\Scripts\python.exe' scripts/benchmark_modal_diagnostics.py `
        --trial $trial --report ($trial + '/modal.json')
    if ($LASTEXITCODE -ne 0) { exit $LASTEXITCODE }
}
exit 0
```

Не запускать несколько таких измеряемых обучений одновременно на одной GPU.
Для измерения графа на одинаковых весах используется отдельный
`benchmark_backward.py --trial <trial> --report <new.json> --trace`;
его профиль не включается во время полных обучений. Для повторного измерения
времени до порога — отдельный протокол в
[time-to-quality-screening.md](time-to-quality-screening.md).
