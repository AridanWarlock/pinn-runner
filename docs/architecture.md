# Архитектура после перехода к Problem API

Решатель остаётся одноразовой файловой задачей. Архитектура делит её на короткие
этапы, а не превращает в сервер или framework с глобальными регистрами.

```text
run.py → TaskApplication
            ├─ TaskSettings ← config.yaml
            ├─ Problem ← functions.py
            ├─ SolverFactory → ProblemAdapter → Torch samplers / FCN / Lightning
            ├─ SolverExecution → train / predict / checkpoint validation
            └─ ArtifactWriter → YAML / JSON / MAT / pickle
```

## Ответственности

`run.py` разбирает CLI и возвращает код завершения. Импорт файла и `--help`
не требуют загрузки Torch. `TaskPaths` разрешает пути и проверяет наличие файлов;
`TaskApplication` соединяет компоненты и записывает ошибки.

`TaskSettings` читает строгий YAML в dataclass-объекты: Domain, Network, Training,
Boundary, Prediction, Runtime. Валидация чисел/выборов отделена от проверки связей.
Ни пользователь, ни YAML не выбирают произвольные внутренние Python-классы.

`Problem` описывает физические поля, функции невязок, начальные и граничные
значения. Он не знает об optimizer, Lightning и файлах результатов.
`Coordinates` именует координаты и параметры; `Equation` предоставляет операции
над полями. Эти классы работают с целым batch, а не с одной точкой.

`ProblemAdapter` переводит понятный пользователю контракт в быстрые vectorized
callbacks sampler-ов. Начальные значения преобразуются Torch → NumPy при
подготовке данных, затем хранятся в Torch. PDE и output transforms не копируют
тензоры на CPU, не проходят через NumPy и не проверяют finite посредством
синхронизации GPU на каждом шаге.

`SolverFactory` один раз вычисляет размер сети, создаёт датасеты, оптимизатор,
checkpoint callback и Trainer. `SolverExecution` отдельно управляет жизненным
циклом train/retrain/predict. `ArtifactWriter` занимается только сохранением
и проверкой конечных результатов. Изменение MAT-формата не требует менять обучение.

`BoundaryPlan` готовит маски граней, значения и объединяет пересечения Дирихле
до начала обучения. `BoundaryConditions` хранит упакованные тензоры и применяет
оператор границы. `SamplerBase` объединяет хранение и slicing: прежние копии
sample_mesh из нескольких классов удалены. `InitialCondition` и `MeshSampler`
содержат только особенности соответствующего ограничения.

`PINNModule` — короткая интеграция с Lightning: forward, накопление loss,
validation, predict и создание optimizer. `PINNDataModule` задаёт именованные
наборы initial/equations/boundaries и loaders. Идентификаторы больше не строятся
из строкового представления bound method.

## Производительность и autograd

Создание объектов контекста имеет небольшой Python overhead, но циклов по
точкам сетки нет. Первые производные по физическим координатам и времени
получаются одним вызовом autograd. Повторные запросы производных одного поля
используют кеш в пределах одного Equation; новый batch получает новый объект.
Производные произвольных выражений не кешируются, чтобы не удерживать чужие графы.

Вторые производные сохраняют create_graph=True, поэтому обучение может
дифференцировать loss по весам сети. Prediction без transform отключает градиенты;
с transform оставляет их, поскольку физическое поле может быть производной
потенциала. Trainer использует inference_mode=False для PDE validation.

Предсказания объединяются одним torch.cat на поле после сбора batch. Это устраняет
многократное копирование уже накопленного результата. Само сохранение всех
предсказаний по-прежнему требует памяти пропорционально размеру сетки.

```sh
python -m scripts.benchmark_equation_api --points 1024 --steps 50
```

Бенчмарк сравнивает ручной autograd и Equation на одной сети: forward, производные
PDE и backward. Перед измерением он проверяет совпадение невязки и градиента весов.
Это локальная CPU-проверка overhead; она не заменяет измерения на RTX/CUDA.

Самописные JIT/CUDA Graphs/AMP, дискретный Runge–Kutta pipeline, inverse parameters,
Hydra-конфиги, старые plotting/download helpers и неработающие upstream-примеры
удалены. Native mixed precision предоставляется Lightning. Поддерживаемые
примеры и тесты используют один актуальный контракт, без слоя совместимости.

## Дальнейшее развитие

Именованные коэффициенты теперь выделены в CoefficientBank и ленивый контекст
Coordinates.coefficients. Формулы работают в Torch; RegularGridCoefficient
хранит фиксированные таблицы как buffers и выполняет differentiable multilinear
sampling. Фабрика проверяет покрытие области, адаптер создаёт контекст на batch,
BoundaryPlan готовит значения conductivity заранее. Это разделение позволяет
добавить иной способ интерполяции без изменений уравнения пользователя.

Кеш коэффициента не образует циклической ссылки на контекст: графы могут
освобождаться после batch. В горячем пути нет проверок finite через GPU sync,
копирования таблиц на CPU и Python-цикла по точкам.

Таблица остаётся фиксированным входом одной задачи, не независимым входом сети.
Для обучения одной сети на произвольных полях потребуется отдельный контракт
представления/кодирования полевого входа. Скалярные параметры уже могут управлять
семейством через формулы, использующие таблицу как основу. См. coefficients.md.

Новый optimizer или sampling strategy добавляются как типизированный выбор в
настройках и соответствующая фабрика. Другой backend может реализовать операции
Equation через адаптер, сохраняя пользовательские имена координат и уравнений.
Новая геометрия потребует контракта выборки точек/нормалей, заменяющего Cartesian
Mesh и BoundaryPlan; код CLI, файлов результатов и определения PDE от этого
не должен зависеть. Эти направления ещё не реализованы.

## Как здесь работают типы Python

Dataclass создаёт конструктор и сравнение полей; frozen запрещает переустановку
атрибутов, но не делает вложенные dict глубоко неизменяемыми. Аннотация
TensorFields — alias для dict[str, Tensor]; она не проверяет размер тензора.
Размер `(N, 1)` и устройство проверяет адаптер во время выполнения.

Callable описывает сигнатуру callback, Protocol описывает интерфейс loader-а
без обязательного наследования. cast сообщает тип mypy, не преобразуя объект;
он нужен в том числе из-за неполных stubs Torch/Lightning. Строгая проверка mypy
покрывает API, runner, samplers, mesh, модель и выбранные численные компоненты;
полный набор файлов перечислен в pyproject.toml. Все аннотации новых компонентов
проверяются вместе с Ruff и CPU-тестами.
