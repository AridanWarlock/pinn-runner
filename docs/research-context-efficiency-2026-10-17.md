# Наблюдения о расходе контекста исследовательского агента

Пользователь попросил замечать основные расходы токенов и способы их уменьшения.
Это наблюдение рабочего процесса, не отчёт биллинга: точной разбивки всего расхода
на вход, выход, внутреннюю обработку и повторно используемый контекст здесь нет.

В подготовке analytic011 шесть крупных выводов инструментов имели оценки
5303, 1141, 4010, 2174, 3708 и 2931 токенов — суммарно около 19,3 тысячи.
Это размеры конкретных выводов по метаданным инструмента, не общий расход чата.
Часть содержания нужна: требования и математическое доказательство нельзя
выбрасывать ради маленького контекста. Основная устранимая часть — повторения.

## Где можно сократить

1. Повторное чтение навыков и рабочего контекста, уже прочитанных в этой беседе.
   Читать один раз; обновлять только изменившийся раздел. Не принимать отсутствие
   текста в ближайших сообщениях за отсутствие ранее изученного документа.
2. Повторение карточки: краткая карточка с критериями, затем полный вид с теми же
   критериями. Полный вид нужен для нового плана/истории/зависимостей, которых нет
   в кратком интерфейсе. После этого не повторять его без причины.
3. Слишком широкий вывод исходников, протоколов и журналов. Сначала точечный `rg`,
   затем нужный диапазон; сравнения и большие JSON обрабатывать программой.
   В контекст возвращать агрегаты, нарушения и конкретные спорные строки.
4. Ожидание GPU. Не перечитывать неизменившийся статус и не анализировать заново
   один и тот же план. Сценарий наблюдения опрашивает API и выводит только смену
   состояния/задачи и короткие сообщения завершённых запусков. Полные журналы
   остаются на Windows; при сбое используется ограниченный `diagnose`.
5. Повторное создание однотипных сценариев сбора/отчёта. Переиспользовать локальный
   сценарий с параметрами, не разворачивать ради этого новый инфраструктурный
   проект и не отвлекаться от точности модели.

## Что применено в текущем блоке

После разрешения на push документы не загружались заново: проверены только
локальные SHA, чистота дерева и публикация. Наблюдение analytic011 использует
существующий API очереди, подавляет одинаковые статусы и сокращает ограниченный
хвост журнала до сообщения о завершённом запуске. Полное сравнение будет
прочитано один раз; итоговые таблицы и статистики сформируются из проверенного
пакета программно. Старые сырые профили и веса не переносятся на Mac.

Сокращается загружаемое дублирующее содержание, а не полнота математических
предпосылок, зарегистрированной матрицы, отрицательных результатов и проверяемых
CSV. Если сокращение скроет нарушение критерия или ограничение вывода, оно
не считается полезной оптимизацией. Для дальнейшей проверки эффекта следует
сравнивать размеры возвращаемых выводов и число чтений на рабочий блок, не
выдавая эти показатели за точное число оплаченных токенов.

## Наблюдение после завершения analytic011

Первичная итоговая сводка двадцати обучений, с диапазонами основных метрик,
проверками памяти и списком нарушений, заняла 697 токенов по метаданным
инструмента. Все двадцать строк и 180 срезов записаны программно в CSV;
их полный JSON в контекст не выводился. Это размер одного вывода, не общий
расход исследования и не измерение оплаченного уменьшения расходов.

Ещё одна возможность — объединять зависимые механические действия в один
контролируемый сценарий с проверкой кода возврата каждого шага, а независимые
проверки выполнять параллельно. Это уменьшает число переходов к модели;
порядок зависимых действий, проверки и разрешения сохраняются.
При сокращении журнала нужно сохранять идентичность записи: текущий случай
очереди может уже смениться, а хвост ещё содержать последнюю запись прошлого
случая. Научные выводы поэтому строятся из полного проверенного пакета,
а сокращённые журналы используются только для наблюдения за продвижением.
