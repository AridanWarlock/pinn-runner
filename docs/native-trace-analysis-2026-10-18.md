# n13b1018120325: что именно сократилось в аналитических производных

## Данные и единица сравнения

Успешный нативный опыт на прежнем стеке, одном сохранённом состоянии
`heat_neumann_polynomial2d`, 1024 фиксированных точках и одинаковых весах.
Происхождение и независимый численный контроль:
`native-profile-result-2026-10-18.md`. Повторного запуска не было.
Штатный collect проверил SHA256 SQLite и нативных отчётов; анализатор сверяет
SHA до и после чтения. Исходные базы открыты в режиме только для чтения.

Общее число ядер 9176/8816 не является равной единицей работы: аналитический
процесс дополнительно выполняет контроль двух правил вне размеченных этапов.
В обоих процессах есть 13 последовательностей NVTX:
одна для подсчёта работы сети, три разогревочные и девять измерительных.
Основное сравнение ниже использует девять одинаковых последовательностей,
с индексами 4…12. Во всех 13 числа ядер каждого этапа также постоянны.

## Привязка событий: почему недостаточно имени потока

CUDA асинхронна: ядро может закончиться после закрытия CPU-диапазона NVTX.
Нельзя требовать, чтобы весь GPU-интервал лежал внутри CPU-интервала.
Сначала используется correlationId для поиска единственного runtime-вызова
запуска, затем проверяются его начало/конец внутри NVTX-диапазона.

Autograd запускает большую часть обратных операций из рабочего CPU-потока.
Проверка только совпадения потока NVTX ошибочно относила лишь 1339 ядер
каждой ветви и создавала ложный вывод о равенстве вычислительной работы.
В реальной базе один CUDA-процесс и два runtime-потока. По кодированию
идентификаторов данного экспорта старшие биты globalTid совпадают с globalPid;
младшие 24 бита — идентификатор потока. Поэтому окончательный анализ проверяет
процесс запуска и процесса NVTX, допускает его рабочие потоки и требует
единственный содержащий диапазон. Перекрытие или неоднозначная корреляция
не угадывается: событие остаётся непривязанным.

Функция `research_tools.trace_analysis.analyze` и независимые SQLite-проверки
в `tests/runner/test_native_trace_analysis.py` воспроизводят это правило.
В тестах специально есть асинхронное завершение ядра, неоднозначный запуск,
пересечение GPU-интервалов и неполная последовательность NVTX.
Это проверка обработки событий, а не подмена численной проверки модели.

## Что говорит математика

Прямое вычисление полиномиальных признаков сохраняет тот же порядок операций.
Изменяется только обратное правило. Для входящих производных a и b:

$$
\frac{\partial L}{\partial\xi}
=\xi(1-\xi)\bigl(6a+32(1-2\xi)b\bigr).
$$

Это упрощённая точная форма обычного цепного правила. Производные a и b
не отсоединяются: их зависимость от координаты и весов нужна для вторых
пространственных производных и градиента PDE-потерь. Полный вывод сохранён
в `neumann-analytic-pullback.md`.

Поэтому одинаковое число ядер прямого поля и уменьшение числа ядер невязки/
градиента согласуются с гипотезой сокращения графа производных, а не с
уменьшением сети или изменением пространства допустимых функций.
Это интерпретация наблюдаемого разложения, а не причинная оценка wall-time.

## Почему это ещё не измерение ускорения

Медианные суммы длительностей ядер в измерительных диапазонах, наносекунды:

| Этап | Autograd | Analytic |
|---|---:|---:|
| Поле | 62561 | 62564 |
| Невязка | 332738 | 254586 |
| Градиент | 556904 | 519080 |

Медианные длительности CPU-диапазонов поля/невязки/градиента:
1,285/6,630/5,085 мс и 1,278/5,095/4,490 мс соответственно.
Они включают инструментирование и поведение конкретного процесса.
Длительности GPU/CPU не складываются без учёта асинхронности и ожиданий.
Для пересекающихся событий отдельно считается длина объединения интервалов,
а сумма не называется реальным временем. Эти временные числа диагностические.

Из доли ядер нельзя вычислить долю p в законе Амдала. Для верхней границы
ускорения нужна неперекрывающаяся доля исходной стоимости:

$$
S_{\max}=\frac1{1-p}.
$$

Здесь такой p для неинструментированного процесса ещё не измерен.
Не заявляем 18,6% ускорения по 18,6% сокращению числа ядер. Отдельный
проспективный протокол без профилировщика —
`frozen-timing-protocol-2026-10-18.md`.

## Оставшиеся границы

Есть настоящий профиль CUDA на этом стеке, однако поле пока не разделено
на сеть и фон; нет полного разложения затрат optimizer/closure и allocations.
Одна сохранённая модель 2D не заменяет матрицу других состояний и 3D.
Cold/warm/predict и память требуют собственного контролируемого измерения.
Полная приёмка TASK-21 не отмечалась автоматически. Defaults прежние.


## Уточнение по семействам ядер

В девяти сопоставимых вызовах число всех наблюдаемых матричных семейств
(`ampere_sgemm_*`, `gemmk1_kernel`, `gemvNSP_kernel`) совпало между правилами.
Разность невязки 82 ядра на вызов состоит из 76 запусков
`vectorized_elementwise_kernel` и 6 `elementwise_kernel`.
Разность градиента 40 состоит из 40 `vectorized_elementwise_kernel`.
Это более точная локализация механизма, чем общее число событий: структура
матричных вычислений сети прежняя, сокращена поэлементная арифметика производных.
Имена семейств агрегированы Nsight; они не дают количества FLOPs внутри ядра.


## Направления копирования и предел данных об аллокациях

[Классификация копирований](experiments/2026-10-18-n13b-copy-directions.csv)
проверена через таблицы `ENUM_CUDA_MEMCPY_OPER` и `ENUM_CUDA_MEM_KIND`,
а не по догадке о числовых кодах. На 13 размеченных вызовов невязки:
221 D2D/905216 байт у обычного правила, 65 D2D/266240 байт у аналитического;
это 17→5 копий на вызов. Для градиента по весам: 26 D2D/106496 байт у обеих
ветвей, то есть 2 копии на вызов. Обмен с CPU к этому сокращению не относится.

[CUDA Runtime API по всей трассе](experiments/2026-10-18-n13b-runtime-api.csv):
`cudaMalloc_v3020` 11 раз и `cudaFree_v3020` 3 раза у каждой ветви.
Суммы длительностей API не считаются временем операции: они включают
инициализацию, завершение, инструментирование и разную контрольную работу.
Одинаковое число CUDA malloc не означает одинаковое число выделений тензоров:
распределитель Torch обслуживает их из своего кеша. Детальное разложение
аллокаций сети/фона/производных из одной этой таблицы не восстанавливается.

## Последующее структурное разложение

Поле теперь разложено по полной сигнатуре ядер на признаки/нормализацию,
сеть со смещениями и фон/восстановление. Уточнено общее имя `kernel`: это
матричный GEMV по полному имени. Получена условная граница только GPU-service,
не end-to-end Амдал: [native-service-budget-2026-10-18.md](native-service-budget-2026-10-18.md).
