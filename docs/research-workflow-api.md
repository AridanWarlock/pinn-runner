# API исследовательской разработки

## Цель и границы

Задачи TASK-27 и последующего этапа: сократить восстановление состояния и
механическую работу агента, сохранив проверяемость численных выводов. Это API
инструментов разработки, а не новый публичный API PINN-решателя. Обучение,
математическое представление и значения по умолчанию этот этап не меняет.

Основной принцип: программа проверяет полноту и считает метрики; агент выбирает
гипотезу, обосновывает математику и интерпретирует ограничения. Короткий результат
должен позволять открыть нужную подробность, не перечитывая все данные.

## Реализованный интерфейс v1

Все команды запускаются Python 3.10+ без Torch. Для этих операций достаточно
системного Python; проектный `.venv` необходим для проверки разработки и обучения.

```sh
python3 scripts/research.py task TASK-21
python3 scripts/research.py status --root numerical-reports/example
python3 scripts/research.py status --remote --root numerical-reports/a008
python3 scripts/research.py collect --root /path/to/study \
  --manifest /path/to/manifest.json --output numerical-reports/example-compact
python3 scripts/research.py compare --bundle numerical-reports/example-compact
python3 scripts/research.py compare --bundle numerical-reports/example-compact --details
```

| Команда | Вход | Выход и побочные действия |
|---|---|---|
| `task` | ID задачи; необязательный `--board` | ID, название, статус, приоритет, зависимости, ссылки и число критериев; `--criteria` добавляет полный текст; без истории и плана. Только чтение CLI Backlog |
| `status` | Каталог серии | Короткое содержимое `status.json`; не читает отчёты обучения |
| `status --remote` | Безопасный относительный путь `numerical-reports/name` | SSH через существующий `gpu_jobs.remote`, неизменяемая проверка Windows-каталога; читает только статус |
| `collect` | Локальные сырые отчёты и явный манифест | Новая папка с `evidence.json`, `final.csv`, `snapshots.csv`; отказывается перезаписывать |
| `compare` | Собранная папка | Проверка парных критериев, отдельно достижение абсолютной точности; `--details` добавляет пары и интервалы |

stdout — один JSON-объект с `contract: 1` и `kind`. Диагностическая ошибка —
один JSON в stderr. Коды: 0 — команда выполнена, а для `compare` парные критерии
выполнены; 1 — корректные данные, но парные критерии не выполнены; 2 — входные
данные, транспорт или контракт некорректны. `collect` сохраняет корректные
неудачные опыты: неудача гипотезы не должна уничтожать доказательства.
Некорректное использование argparse имеет обычный код 2 и текст справки.

`comparison_passed: true` **не означает** достижения абсолютной точности,
причинного доказательства ускорения, чистоты исходного кода или разрешения
сменить основной режим. Эти утверждения имеют отдельные поля/предпосылки.

## Манифест анализа v1

Это строгий JSON с единственным поддерживаемым набором полей. Неизвестные поля
не игнорируются. Полные рабочие примеры —
[импорт 008](experiments/2026-10-17-a008-import-manifest.json) и
[импорт 009](experiments/2026-10-17-a009-import-manifest.json).

- `contract`: 1.
- `registration`: `prospective` или `retrospective_import`. Это декларация
  происхождения анализа, не автоматически доказанная регистрация до обучения.
- `revision`: полный SHA исходного кода обучения, 40 строчных hex-символов.
- `reports`: явные относительные POSIX-пути к итоговым `report.json`.
  Абсолютные пути, выход за корень, повторные файлы и ссылки наружу запрещены.
  Рекурсивный обход не используется: родительский отчёт и дочерние процессы
  нельзя случайно посчитать двумя независимыми опытами.
- `expected_trials`: полная ожидаемая матрица. Каждая строка содержит
  `case`, `seed`, `backend`, `lifting`, `backward`, `background`, `spatial_encoding`.
  На случай/seed требуется ровно один контроль и один кандидат.
- `report_parameters`: точные значения `adam_steps`, `lbfgs_snapshots`,
  `constraints`, `points_override`, `lbfgs_tolerance_change`, `execution_lifecycle`.
  Здесь поддерживается только `isolated_trials`, не повторное использование
  процесса. Дубли и неупорядоченные контрольные шаги запрещены.
- `case_limits`: для каждого случая свои положительные конечные пороги метрик.
  Обязательны `relative_l2`, `final_relative_l2`, `pde_rmse`;
  `mode_relative_l2` добавляется только там, где определена соответствующая мода.
- `physical_limits`: `initial_rmse`, `boundary_max`.
- `comparison`: полные пять полей каждой ветви `baseline`/`candidate`,
  `quality_factor`, `median_training_ratio_max`, `worst_training_ratio_max`.

Манифест фиксирует ожидаемую матрицу независимо от фактически найденных файлов.
Нельзя генерировать ожидание по имеющимся результатам и считать это доказательством
полноты. Для старых серий ожидание сверяется с исходным протоколом. Примеры 008/009
созданы после обучения и явно помечены ретроспективным импортом; они не заменяют
[исходные протоколы](analytic-neumann-learning-2026-10-17.md).

## Приёмка доказательств

Сборщик принимает текущий контракт отчёта сходимости 3, только `completed`.
Проверяет весь бюджет, пороги, среду и SHA, точную матрицу, полноту расписания
состояний, конечность/неотрицательность метрик, неубывание времени. Каждая пара
должна иметь одинаковые отпечатки начальных весов и фиксированных PDE-точек,
а также одинаковый размер и режим замера предсказания.

Независимая оценка должна сообщать `eager` / `general` / `autograd`, в том числе
для аналитического кандидата. Заявленное аналитическое исполнение должно
соответствовать фактическому правилу производных. Дефект начальных и граничных
условий проверяется во всех сохранённых состояниях, а не только в последнем.
Пропущенная метрика, NaN, отсутствующая грань в виде пустого списка или
несопоставимые веса — ошибка данных, а не успешный опыт.

Происхождение файлов сохраняется через SHA-256 исходных отчётов и манифеста.
Это контроль связи с исходными файлами, **не электронная подпись**. Сохранённые
флаги прохождения и пересечения заново вычисляются при сравнении.

Для `prospective` требуется явно чистый рабочий каталог в отчётной среде.
В 008/009 среда записала `working_tree_dirty: true`: импорт сохраняет этот факт
и требует отдельной проверки происхождения. Один SHA не доказывает отсутствие
изменений исходников; нельзя скрывать эту оговорку под успешными численными
критериями. Будущий исполнитель должен работать из неизменяемого Git-снимка.

## Математический смысл критериев

Пусть m — одна метрика, A — контроль, B — кандидат, ε — абсолютный целевой порог,
α — зарегистрированный множитель допуска. Сохранение качества проверяется так:

$$
m_B \le \max(\alpha m_A,\varepsilon).
$$

Абсолютное попадание в целевую точность — другое утверждение:

$$
m_B\le\varepsilon.
$$

Поэтому два одинаково неточных метода способны пройти критерий сохранения
качества и одновременно не решить задачу с требуемой точностью. В выводе эти
события разделены. Для подтверждения точности нужны два соседних сохранённых
состояния, прошедших все метрики. Первое пересечение даёт интервал между
контрольными измерениями; линейная интерполяция запрещена. Если уже первое
состояние прошло порог, интервал помечается `left_censored`.

Время обучения включает предыдущие контрольные сохранения; независимая оценка
не включается. Отношение времени считается отдельно для каждой пары, затем
медиана по seed; нельзя подменять его отношением двух независимо взятых медиан.
Это время фиксированного бюджета. Время до точности выводится отдельно через
интервалы и момент подтверждения. Быстрый неточный метод не объявляется
ускорением достижения точности.

Граничная ошибка температуры не равна дефекту оператора Неймана. Сборщик
использует `boundary_operators[*].max_error` для физических ограничений.
Дискретная независимая проверка не доказывает непрерывной оценки ошибки PDE.
Полные математические ограничения: [контекст агента](agent-research-context.md).

## Хранение и ограничения первого этапа

`evidence.json` нужен для последующего машинного сравнения и хранится в
игнорируемом `numerical-reports`, не копируется в Git по умолчанию. В нём только
метрики контрольных состояний, без полных временных профилей и весов. В Git
попадают небольшие CSV/сводки и необходимые манифесты. Математические Markdown
не сокращаются ради объёма данных. Большие журналы не отправляются в stdout.

Реализован сбор **локально доступных** отчётов. Удалённый перенос, общий запуск
произвольной серии, отмена, восстановление после обрыва и регистрация очереди
ещё не реализованы новым API. `gpu_jobs.py` остаётся отдельным существующим
API ограниченных benchmark_solutions; он не запускает произвольный манифест
сходимости. Новая команда не создаёт GPU-процессы и не меняет Backlog.

Коллектор проверяет присутствие численных дефектов границ, но контракт 3 ещё
не фиксирует ожидаемый список имён/осей/типов всех граней в манифесте. Он не
доказывает полноту геометрического покрытия и не проверяет исходные веса заново.
Это явная граница доказательства, которую нужно закрыть следующим контрактом,
а не выводить из количества имеющихся ошибок.

## Следующий этап: удалённый исполнитель

Цель — заменить временные PowerShell/Python-рецепты, используя существующие
`gpu_jobs.py`, `gpu_worker.py`, `convergence_processes`, без второго механизма
блокировки GPU. Требования, а не обещание существующих команд:

1. `submit` принимает заранее опубликованный протокол; фиксирует его хеш и
   точный опубликованный SHA до старта. Нельзя молча тестировать новый HEAD.
2. Отдельный неизменяемый снимок внутри `C:\Projects\pinn-runner`; запуск из
   обязательного рабочего каталога. Все кэши и временные файлы внутри проекта.
3. Идемпотентный ID: повторный запрос не запускает вторую копию. Одна GPU-очередь,
   явные состояния `queued/running/completed/failed/timed_out/unknown`.
   Обрыв SSH не считается автоматически ни успехом, ни остановкой обучения.
4. Длительное обучение переживает завершение управляющего запроса; статус
   содержит время последнего подтверждения и прогресс без чтения полных отчётов.
5. `collect --remote` сначала валидирует данные на Windows, затем передаёт
   компактные результаты. Сырые данные остаются доступными по явному запросу.
6. Таймаут и отмена завершают дерево процессов; восстановление проверяет
   состояние владельца блокировки и процесса, а не только давность файла.
7. Статус процесса, полнота серии и качество решения — разные поля. Общий
   `completed` никогда не означает автоматически «решение верно».
8. Контракт фиксирует ожидаемые грани и дополнительные параметры точности,
   архитектуры/конфигурации. Сравнение разных представлений может иметь разные
   начальные веса: для него нужен отдельный явно обоснованный режим, не обход
   текущей проверки одинаковых отпечатков.
9. Тесты на Mac используют поддельный транспорт, обрыв связи, повреждённый файл,
   повторный ID, неверный каталог и частичный результат. Затем короткая реальная
   Windows-проверка транспорта, не новое длительное обучение.

Не делать в этом этапе: новую серверную платформу, веб-интерфейс, обновление
Torch, автоматическое изменение математических ограничений или основных настроек.
