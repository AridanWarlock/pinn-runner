# План развития PINN runner

## Где мы сейчас

Основа целевой системы реализована: одноразовый файловый runner; обучение без
эталонного решения; 1D/2D/3D; скалярные параметры как входы сети; явные начальные
и граничные условия; коэффициенты через формулы и пространственные NPZ-таблицы;
новый типизированный API, конфиги без классов backend, разделённые компоненты.
Это рабочая основа, а не подтверждение качества решения произвольной PDE.

На RTX проверены производные, обучение и перенос checkpoint CPU ↔ CUDA.
Три аналитические PDE прошли численную приёмку и повторное сравнение с baseline.
Не считаем готовыми: точность произвольных реальных задач, разумную стоимость
больших 3D-сеток, CUDA-производительность и устойчивость mixed precision. MPS также пока не проверен. Тензор коэффициента сейчас задаёт
**известное поле конкретной задачи**; сеть не принимает произвольное новое поле
без переобучения. Обратные задачи по наблюдениям остаются вне текущего объёма.

Процент готовности здесь мало полезен: интерфейс уже развит, но численная
пригодность и эксплуатация требуют отдельных критериев приёмки.

## Очерёдность и критерии завершения

1. **Windows/RTX подключён.** GPU acceptance проверил 1D/2D/3D-производные,
   backward, реальное обучение и перенос checkpoint CPU ↔ CUDA. Запуск через SSH,
   все рабочие файлы и временные данные остаются в C:\Projects\pinn-runner.
2. **Базовая численная приёмка выполнена.** Теплопроводность 2D, перенос 1D и
   нелинейный Бюргерс с известным источником проверены на независимых точках,
   с seeds 1234 и 4321 и по 3000 шагов. Повторные шесть обучений прошли сравнение
   с зафиксированным baseline. Методика и результаты:
   [numerical-benchmarks.md](numerical-benchmarks.md). Следующее расширение:
   длительная приёмка 3D, параметрических семейств и многополевой системы;
   текущие три задачи не покрывают все возможности и все виды PDE.
3. **Управление обучением.** По результатам предыдущего этапа ввести явные веса
   компонент loss и отчёт по каждой компоненте; затем сравнить Adam и Adam→L-BFGS.
   Не вводить адаптивные веса и новые оптимизаторы одновременно: иначе нельзя
   понять причину улучшения. Приёмка: конкретная задача сходится лучше в том же
   бюджете либо быстрее до заданной точности.
4. **Память и стоимость 3D.** Убрать необходимость полного декартова произведения
   для подготовки всех данных, отделить генерацию точек границ/IC от PDE,
   организовать пакетный predict и запись результата. Сначала измерить RAM/VRAM
   и масштабирование. Приёмка: большая задача не требует хранения всей сетки
   обучения и всех выходных тензоров сразу; порядок результатов сохранён.
5. **Production-контейнер.** Повторить acceptance и численные задачи в том Docker,
   который запускает внешний сервис, с CUDA. Зафиксировать зависимости, лимиты
   времени/памяти и набор артефактов при успехе/ошибке. Приёмка: чистый контейнер
   обрабатывает входной каталог и завершает процесс с корректным кодом.
6. **Расширения после базовой приёмки.** Интерфейсы разрывных материалов,
   анизотропный тензор теплопроводности, более сложная геометрия, поля коэффициента
   как семейства входов. Последний пункт может потребовать параметризации поля
   базисом либо operator network; текущая координатная FCN этого сама не даёт.

## Рабочий цикл двух машин

Mac: типы, lint, быстрые тесты при разработке; полный набор на завершении блока.
Windows: GPU acceptance после изменений autograd, сети, переноса устройств,
таблиц коэффициентов, checkpoint или версий Torch/Lightning. Длительные проверки
сходимости запускаем на завершении численного блока. Docker — перед выпуском.

Передаём изменения через один commit Git, отчёты сравниваем по его SHA. Пока не
проверяем CUDA на Mac и не считаем CPU-прогон заменой GPU-прогона. Инструкции и
команды Windows: [cuda-testing.md](cuda-testing.md).
