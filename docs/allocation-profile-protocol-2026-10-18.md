# TASK-21: ограниченный контроль распределителя Torch

## Один вопрос

Какие выделения и освобождения CUDA-памяти видит **распределитель Torch**
при вычислении сети, фона, физической невязки, редукции потерь и градиента
по весам? Нативная n13b уже показала запуски/копирования, но одинаковое число
cudaMalloc не отвечает на этот вопрос из-за кеширующего распределителя.
Нативный опыт не повторяется, Nsight и повышенные права не используются.

## До запуска

Сохранённая модель та же, что в n13b: полином2D, eager/seed19, `lb-2000.pt`
из analytic012. SHA256 весов/конфигурации закрепляются в отдельном машинном
протоколе contract7, `allocation-profile`; SHA кода и протокола раздельны.
Две свежие последовательные ветви autograd/analytic, 1024 одинаковые точки
из CPU-генератора seed19, перенос на CUDA. Сеть32×32×32 и физическая задача
из сохранённой конфигурации. RTX4070Ti, Torch2.1.0+cu118, CUDA11.8,
FP32/TF32 off проверяются в родительском и дочерних процессах.

В каждой ветви две обычные оценки дают независимый контроль analytic против
autograd, одна обычная оценка выбранного правила задаёт опорный градиент,
одна оценка с разметкой собирает память. Итого8 вычислений функционала,
из них2 под профилировщиком. Шагов оптимизатора и изменения весов нет.

## Разметка и смысл величин

Физическое поле вычисляется по тому же контракту `PINNModule.forward`:
сначала `model.net(spatial,time)`, затем `model.output_fn(outputs,*columns)`.
Они разнесены на две диагностические области без изменения функций.
Остальные области — физическая невязка, редукция потерь и backward по всем
параметрам. Потери и градиенты разложенной оценки сравниваются с обычным
вызовом: rtol2e-4, atol1e-8 для потерь, atol2e-7 для градиента.
Независимый autograd-контроль: абсолютная разность потерь не более1e-8;
относительная L2 градиента не более2e-4 либо максимальная абсолютная не более2e-7.
Состояние модели/буферов и SHA исходных весов не меняются.

Используется CPU-активность Torch profiler с `profile_memory=True`.
Она не требует CUPTI для времени CUDA-ядер. Проверяется, отдаёт ли этот
конкретный стек CUDA-события `[memory]`; наличие CPU-активности само по себе
не считается доказательством их наличия. Если CUDA-событий нет, это полный
отрицательный диагностический результат, а не основание для повторов с
неограниченной перенастройкой среды.

Для каждой области сохраняются числа положительных/отрицательных событий
распределителя, суммы выделенных/освобождённых байтов, allocated/reserved
до/после и соответствующие пики. События рабочего потока autograd допускаются
по тому же процессу и времени содержащей неперекрывающейся области.
CPU-память, другой процесс и события вне области исключаются.

Эти события описывают распределитель, а не гарантированное число Python-тензоров
или обращений cudaMalloc. Пик региона измеряется после сброса статистики,
но **без очистки кеша**. До/после области есть синхронизация: это диагностика,
не время обычного обучения. Суммы пиков разных областей не складываются:
одни и те же живые тензоры переходят между областями, освобождение графа
при backward может дать отрицательное изменение живой памяти.

## Окончание и хранение

Общий таймаут300с, два процесса, без автоматического продления и обучения.
Штатные collect/compare проверяют происхождение, равенство состояний ветвей,
пять областей, численные контроли, целостность и наличие CUDA-memory events.
Нет событий — compare=false при сохранении корректного отрицательного пакета;
ошибка/неполный отчёт диагностируются штатно, completion-маркеры не подделываются.

Полные Chrome-трассы остаются в Windows внутри нового каталога GPU-очереди.
В Git — десять строк фаз, компактные инварианты и русский отчёт.
Время под профилировщиком не используется как доказательство ускорения;
показатели скорости остаются за timing014/lbfgs015. Defaults не меняются.
