# Пространственные коэффициенты

Коэффициент — известный вход физической задачи: теплопроводность, плотность,
скорость реакции и т.п. Это отдельный контракт от выходных полей сети и от
скалярных параметров семейства задач. Он не обучается по наблюдениям.

`e.coefficients[name]` в PDE и `c.coefficients[name]` в initial/boundary/transform
возвращают Tensor `(N, 1)` для текущих координат. Имена должны отличаться от
координат, скалярных параметров, полей и уравнений. Старые задачи без coefficients
работают без изменений.

## Формула в functions.py

```python
import torch
from pinnstorch.api import Coordinates, Equation, Problem, TensorFields


def conductivity(c: Coordinates) -> torch.Tensor:
    return 0.1 + 0.2 * c.x + 0.2 * c.y


def heat(e: Equation) -> torch.Tensor:
    flux = {
        axis: e.coefficients["conductivity"] * derivative
        for axis, derivative in e.gradient("T").items()
    }
    return e.dt("T") - e.divergence(flux)


def initial(c: Coordinates) -> TensorFields:
    return {"T": torch.sin(torch.pi*c.x) * torch.sin(torch.pi*c.y)}


problem = Problem(
    fields=("T",), equations={"heat": heat}, initial=initial,
    coefficients={"conductivity": conductivity},
)
```

Callback получает Coordinates, возвращает число либо Tensor `(N, 1)` на том же
устройстве. Формулы работают в Torch поточечно и могут зависеть от времени,
скалярных параметров и других коэффициентов. Зависимости разрешаются лениво;
повторный запрос в одном контексте возвращает кешированный Tensor. Циклы
зависимостей вызывают понятную ошибку. Между batch кеш не сохраняется.

Для пространственно меняющегося коэффициента консервативная теплопроводность
имеет вид T_t=div(c·grad(T)). Запись c·laplacian(T) пропускает grad(c)·grad(T).
Формулы должны сохранять autograd: не используйте NumPy, detach, item или
копирование на CPU внутри PDE.

## Табличное поле в config.yaml

```yaml
coefficients:
  conductivity:
    file: conductivity.npz
```

Путь относительный, файл должен находиться внутри input-dir. Он не является
эталонным решением T. Содержимое NPZ — один или несколько векторов x/y/z и
массив values; другие ключи запрещены. Объектные/pickle массивы не загружаются.

```python
import numpy as np
x = np.linspace(0, 1, 9)
y = np.linspace(0, 1, 7)
values = 0.1 + 0.2*x[:, None] + 0.2*y[None, :]
np.savez("conductivity.npz", x=x, y=y, values=values)
```

| Поле | Формат |
| --- | --- |
| x/y/z | Одномерный конечный строго возрастающий вектор, минимум две точки |
| values | Конечный числовой массив с формой `(Nx[, Ny, Nz])` |
| Порядок | Только присутствующие оси в порядке x, y, z; ij indexing |

Поле может зависеть только от x в 3D-задаче: отсутствующие оси не добавляются в
values. Все присутствующие оси должны существовать в domain.space. Таблица
обязана покрывать весь интервал задачи по своим осям. Её узлы могут быть
неравномерными и не обязаны совпадать с сеткой PDE, LHS или предсказания.

Формулы должны быть детерминированными и не менять состояние между вызовами.
Зависимость коэффициента от предсказанного T вычисляйте внутри PDE напрямую: контекст
коэффициентов содержит координаты и параметры, а не выходы сети.

Вычисления runner используют float32. Слишком близкие узлы, которые сливаются
после преобразования в float32, и переполнение значений отвергаются.
`allow_extrapolation` не разрешает выход за покрытие таблицы: коэффициент за её
пределами не задан. Проверка покрытия делается при подготовке задачи.

### Интерполяция и производные

Используется multilinear-интерполяция: линейная в 1D, билинейная в 2D и
трилинейная в 3D. Все 2, 4 или 8 углов каждой ячейки обрабатываются одним батчированным расчётом;
цикла по отдельным точкам нет. Геометрия углов готовится один раз и перемещается
на устройство модели вместе с таблицей. Интерполяция выполняется в Torch на устройстве
модели и сохраняет производные по координатам.

Номер ячейки выбирается searchsorted по detached координате. Это дискретный
выбор; градиент идёт через дробное положение внутри ячейки, где остаётся
исходная координата. Поэтому div(c·grad(T)) учитывает изменение табличного c.

Поле непрерывно, но его производная обычно имеет скачки на внутренних узлах.
На узле выбирается ячейка справа, на верхнем краю — последняя ячейка. Производная
там односторонняя; методы не обещают глобальную гладкость или классические
производные любого порядка. Скачки самого c и явные условия на интерфейсах
материалов требуют отдельной постановки; текущая таблица их не моделирует.

Для программного определения вместо файла доступен
`pinnstorch.RegularGridCoefficient(axes={"x": tensor_x}, values=tensor_values)`.
Передайте объект в Problem.coefficients. Порядок values соответствует порядку
axes в переданном mapping. В файловом NPZ порядок всегда x/y/z.
При прямом использовании класса вне runner вызывающий код отвечает за покрытие:
низкоуровневый forward продолжает крайние ячейки линейно за границей таблицы.

## Семейство полей со скалярным управлением

Можно загрузить основу как таблицу и менять её амплитуду входным параметром:

```yaml
domain:
  space:
    x: {interval: [0, 1], points: 32}
  time: {interval: [0, 1], points: 8}
  parameters:
    amplitude: {interval: [0.1, 0.5], points: 5}
coefficients:
  base: {file: base.npz}
```

```python
def conductivity(c: Coordinates) -> torch.Tensor:
    return c.parameters["amplitude"] * c.coefficients["base"]
```

В Problem.coefficients задаётся conductivity, в YAML — base. Нельзя определять
одно имя одновременно в обоих местах. Сеть получает amplitude как обычный
вход и обучается для соответствующего семейства задач.

Произвольный новый массив c(x,y,z) не является самостоятельным входом обученной
сети. Для fixed table сеть решает одну конкретную физическую задачу. Обучение
одной сети на произвольных новых полях потребует представления полевого входа
и другой архитектуры; здесь этот режим не реализован.

## Тепловой поток

```yaml
boundaries:
  - kind: heat_flux
    field: T
    axis: x
    side: upper
    conductivity: conductivity
    value: 0
```

conductivity может быть положительным числом, именем положительного скалярного
параметра или именем коэффициента. Для именованного поля проверяются конечность,
положительность и форма на сетке задачи перед обучением. Значения на границах
готовятся заранее и хранятся вместе с targets: повторной интерполяции на каждом
шаге boundary loss нет. Поле предписано и не зависит от весов сети, поэтому такое
отсоединение не меняет градиент loss по весам. Производные границ по-прежнему
считаются по T, а правило исключения углов/рёбер сохраняется.

## Checkpoint и результаты

Табличные оси и values — buffers nn.Module. Они перемещаются вместе с моделью
и записываются в checkpoint, но не входят в optimizer parameters.

Checkpoint также содержит coefficient_signature. Для таблицы это SHA-256
канонических имён/форм/числовых массивов, а не байтов ZIP-файла: переупаковка
того же NPZ не меняет идентичность. Для формул используется SHA-256 всего
functions.py, поскольку формула может зависеть от helpers и глобальных констант.

При predict/retrain имена и сигнатуры должны совпасть. Для формул даже изменение
комментария или посторонней функции меняет сигнатуру: проверка намеренно
консервативна. Зависимости из внешних модулей автоматически не отслеживаются;
за их неизменность отвечает автор задачи. Для нового поля запускайте train.

В результатах `problem.json` перечисляет коэффициенты, `coefficients.json`
содержит сигнатуры и способ интерполяции таблиц. `predictions.mat` содержит
предсказанные поля сети, а не копию коэффициентной таблицы. Входные файлы
коэффициентов нужны и при predict для проверки задачи и возможного transform.

## Пример и проверки

[heat_spatial_coefficient](../examples/heat_spatial_coefficient) генерирует поле
0.1+0.2x+0.2y, обучает 2D-модель три шага и выполняет predict. Это проверка запуска,
не доказательство сходимости. Ни data.mat, ни температурных labels нет.

Тесты проверяют точные multilinear-функции в 1D/2D/3D, неравномерные ячейки,
производные/невязки, backward через вторые производные T, кеш, зависимости,
валидацию файлов, heat_flux, реальные train/predict процессы и отказ при
подмене поля. Они выполняются на CPU; CUDA/MPS/mixed precision отдельно не проверены.


Для локального замера:

```sh
python -m scripts.benchmark_coefficients
```

Бенчмарк сравнивает формулу и эквивалентную таблицу на одной сети, 1024 точках
и полной цепочке PDE → backward. Проверяется совпадение невязок и градиентов
всех весов. PDE-loss не зависит от постоянного output bias; его отсутствующий
градиент сравнивается как нулевой. Числа CPU не прогнозируют скорость CUDA.
