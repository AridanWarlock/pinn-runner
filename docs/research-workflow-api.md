# API исследовательской разработки

## Численная приёмка (contract 6)

`numerical-acceptance` запускает через ту же очередь только один из шести
фиксированных наборов:20 сценариев `test_neumann_polynomial_pullback.py`
либо6 файловых `test_neumann_feature_runner.py`, либо16 численных
`test_variable_conductivity_network.py`, либо8 `test_nonheat_network.py`, либо2 публичных файловых
`test_nonheat_runner.py` для переноса/Бюргерса. Последние проверяют train,
точную загрузку,predict5×6 и retrain,3 Adam+2 L-BFGS в обычном fit
и1 Adam с learning_rate1e-300 без L-BFGS для точной загрузки. Всего6 малых
fit и8 CLI-процессов; CUDA-хранилища проверяются в сохранённой модели.
Отдельный `test_burgers_hard_network.py` содержит4 аналогичных контроля
существующего hard_initial_dirichlet для Бюргерса (2 FP64 конечные разности);
он не меняет прежний список8 сценариев и сохраняет их воспроизводимость.
Набор nonheat проверяет перенос/Бюргерс ×FP32/64 ×seed19/73, все2241
параметр и4 совместные конечные разности без обучения. Отдельный
`helper_sha256` фиксирует импортируемый `scripts/audit_nonheat.py`;
канонический SHA и неизменность сырых байтов проверяются до/после.
Набор переменной теплопроводности проверяет формулу/таблицу,
все весовые градиенты, FP32/FP64 и1D/2D без шагов оптимизатора; один seed19.
Протокол фиксирует
список nodeid, SHA256 файла и CUDA-среду; произвольные pytest-файлы не допускаются.
Для идентичности Git-текста задан `test_hash_mode=lf-normalized`: учитывается
только перенос CRLF→LF; сырые SHA до/после также обязаны совпасть.
Сбор сверяет setup/call/teardown и сырой журнал: пропуски, xfail/xpass и ошибка
teardown не считаются успехом. При нарушенной полноте публикации пакета нет.
В геометрическом наборе обучения нет, в файловом есть только малые
диагностические fit; оценки скорости нет в обоих. Предпосылки:
`geometry-acceptance-protocol-2026-10-18.md` и
`lifecycle-acceptance-protocol-2026-10-18.md`.
Переменная теплопроводность: `variable-conductivity-cuda-protocol-2026-10-19.md`.

## Одиночная абсолютная точность (contract 2)

Вместо `comparison` задаётся `absolute_quality`: ровно одна конфигурация
`eager/recursive/all/general/identity`; исходные soft-условия либо `hard_initial_dirichlet` только для Бюргерса. Этот режим
ограничен зарегистрированными `advection`/`burgers`. `problem_sha256`
фиксирует LF-нормализованный исходник каждой PDE, грани сверяются с каталогом;
лишнее выходное условие переноса отвергается. Для точного Бюргерса
сверяется фактически исполненный constraint_kind; число исходов не удваивается. Каждая пара case/seed встречается
ровно один раз. Старые парные протоколы сохраняют прежние требования.

Обязательны общий/финальный/худший временной относительный L2 и RMS PDE,
отдельные IC RMS и максимум заданных граничных значений. Финальный успех
требует всех шести порогов. Промежуточные неудачи сохраняются; IC/BC входят
также в диагностику соседних успешных срезов. Для soft нельзя требовать,
чтобы раннее необученное состояние уже выполняло финальные условия.
`compare` возвращает `absolute-quality-comparison`, `passed`, `results`
с `failed_metrics`, `timing_passed=null`. Время/память диагностические;
никакой проверки ускорения или сравнения одинаковых моделей нет.
Используются тот же `research_run.py`, свежие дочерние процессы,
общая блокировка, неизменяемый снимок, `collect`/`compare` и пакет `bundle.json`.
Численные неудачи дают полный пакет с `comparison_passed=false`, а не потерю
данных. Неполная серия по-прежнему отвергается.

## Ограниченный контроль L-BFGS (contract 5)

`kind: lbfgs-timing` использует ту же неизменяемую очередь, общую GPU-блокировку,
таймаут, `plan/submit/status/collect/compare`; отдельного SSH-исполнителя нет.
Матрица ограничена полиномиальным 3D, источниками seed 19/4321, тремя парами
и десятью внешними шагами в двух схемах измерения. Подробности и заранее
заданные критерии: `lbfgs-step-protocol-2026-10-18.md`.

Полное время измеряется отдельно от диагностического разложения замыканий.
`timing_paths_match` и отпечатки требуют одной траектории этих двух проходов
из одинакового состояния. Между analytic/autograd допускаются только заранее
заданные численные отклонения. Прогрев и измерения восстанавливают исходные
веса; исходные файлы `.pt` не меняются. В пакет входит `evidence.json` с
12 компактными отчётами, сводный CSV и штатный `bundle.json`; подробные
журналы остаются Windows-артефактами и защищены SHA256. Отрицательные
скоростные/численные результаты сохраняются, неполная серия не принимается.

## Цель и границы

Задачи TASK-27 и последующего этапа: сократить восстановление состояния и
механическую работу агента, сохранив проверяемость численных выводов. Это API
инструментов разработки, а не новый публичный API PINN-решателя. Обучение,
математическое представление и значения по умолчанию этот этап не меняет.

Основной принцип: программа проверяет полноту и считает метрики; агент выбирает
гипотезу, обосновывает математику и интерпретирует ограничения. Короткий результат
должен позволять открыть нужную подробность, не перечитывая все данные.

## Реализованный интерфейс

Управляющие команды запускаются Python 3.10+ без импорта Torch. Обучение
выполняется только отдельными Windows-процессами из проектного `.venv`.

```sh
python3 scripts/research.py submit --protocol-commit FULL_SHA \
  --protocol-path docs/experiments/protocol.json --job-id study-001
python3 scripts/research.py status --remote --job-id study-001
python3 scripts/research.py cancel --job-id study-001
python3 scripts/research.py collect --remote --job-id study-001 \
  --output numerical-reports/study-001-compact
python3 scripts/research.py diagnose --remote --job-id study-001
python3 scripts/research.py diagnose --remote --job-id study-001 \
  --log run --lines 10 --max-bytes 2048
python3 scripts/research.py tasks
python3 scripts/research.py task TASK-21
python3 scripts/research.py status --root numerical-reports/example
python3 scripts/research.py status --remote --root numerical-reports/a008
python3 scripts/research.py collect --root /path/to/study \
  --manifest /path/to/manifest.json --output numerical-reports/example-compact
python3 scripts/research.py compare --bundle numerical-reports/example-compact
python3 scripts/research.py compare --bundle numerical-reports/example-compact --details
```

| Команда | Вход | Выход и побочные действия |
|---|---|---|
| `submit` | Опубликованный commit протокола, путь, ID, таймаут; необязательный `--probe` | Обновляет Windows checkout через ff-only, проверяет опубликованные объекты Git, создаёт отдельный снимок и отсоединённый процесс; повтор ID не запускает новую копию |
| `status --remote --job-id` | ID | Состояние процесса, время подтверждения, прогресс по случаям; не качество решения |
| `cancel` | ID | Запрос отмены; завершение подтверждается следующим статусом, не самим фактом записи запроса |
| `collect --remote` | ID и новая папка | Проверяет/сокращает отчёты на Windows, передаёт только машинное доказательство и пишет локальную папку; stdout короткий |
| `diagnose` | ID и `--remote` либо локальная копия `--root`; необязательный ограниченный хвост журнала | Статус/причина, список журналов; не запускает обучение. [Детали](research-diagnostics.md) |
| `task` | ID задачи; необязательный `--board` | ID, название, статус, приоритет, зависимости, ссылки и число критериев; `--criteria` добавляет полный текст; без истории и плана. Только чтение CLI Backlog |
| `status` | Каталог серии | Короткое содержимое `status.json`; не читает отчёты обучения |
| `status --remote` | Безопасный относительный путь `numerical-reports/name` | SSH через существующий `gpu_jobs.remote`, неизменяемая проверка Windows-каталога; читает только статус |
| `collect` | Локальные сырые отчёты и явный манифест | Новая папка с `evidence.json`, `final.csv`, `snapshots.csv`, `bundle.json`; отказывается перезаписывать |
| `compare` | Собранная папка | Проверка парных критериев, отдельно достижение абсолютной точности; `--details` добавляет пары и интервалы |

stdout — один JSON-объект с `contract: 1` и `kind`. Диагностическая ошибка —
один JSON в stderr. Коды: 0 — команда выполнена, а для `compare` парные критерии
выполнены; 1 — корректные данные, но парные критерии не выполнены; 2 — входные
данные, транспорт или контракт некорректны. `collect` сохраняет корректные
неудачные опыты: неудача гипотезы не должна уничтожать доказательства.
Некорректное использование argparse имеет обычный код 2 и текст справки.

`comparison_passed: true` **не означает** достижения абсолютной точности,
причинного доказательства ускорения, чистоты исходного кода или разрешения
сменить основной режим. Эти утверждения имеют отдельные поля/предпосылки.

## Манифест анализа и исполнения

Это строгий JSON с единственным поддерживаемым набором полей. Неизвестные поля
не игнорируются. Полные рабочие примеры —
[импорт 008](experiments/2026-10-17-a008-import-manifest.json) и
[импорт 009](experiments/2026-10-17-a009-import-manifest.json).

- `contract`: 1 для прежнего анализа, 2 для нового удалённого исполнения.
- `registration`: `prospective` или `retrospective_import`. Это декларация
  происхождения анализа, не автоматически доказанная регистрация до обучения.
- `revision`: полный SHA исходного кода обучения, 40 строчных hex-символов.
- `reports`: явные относительные POSIX-пути к итоговым `report.json`.
  Абсолютные пути, выход за корень, повторные файлы и ссылки наружу запрещены.
  Рекурсивный обход не используется: родительский отчёт и дочерние процессы
  нельзя случайно посчитать двумя независимыми опытами.
- `expected_trials`: полная ожидаемая матрица. Каждая строка содержит
  `case`, `seed`, `backend`, `lifting`, `backward`, `background`, `spatial_encoding`.
  На случай/seed требуется ровно один контроль и один кандидат.
- `report_parameters`: точные значения `adam_steps`, `lbfgs_snapshots`,
  `constraints`, `points_override`, `lbfgs_tolerance_change`, `execution_lifecycle`.
  Здесь поддерживается только `isolated_trials`, не повторное использование
  процесса. Дубли и неупорядоченные контрольные шаги запрещены.
- `case_limits`: для каждого случая свои положительные конечные пороги метрик.
  Обязательны `relative_l2`, `final_relative_l2`, `pde_rmse`;
  `mode_relative_l2` добавляется только там, где определена соответствующая мода.
- `physical_limits`: `initial_rmse`, `boundary_max`.
- `comparison`: полные пять полей каждой ветви `baseline`/`candidate`,
  `quality_factor`, `median_training_ratio_max`, `worst_training_ratio_max`.

Манифест фиксирует ожидаемую матрицу независимо от фактически найденных файлов.
Нельзя генерировать ожидание по имеющимся результатам и считать это доказательством
полноты. Для старых серий ожидание сверяется с исходным протоколом. Примеры 008/009
созданы после обучения и явно помечены ретроспективным импортом; они не заменяют
[исходные протоколы](analytic-neumann-learning-2026-10-17.md).


### Дополнения контракта 2

Удалённое исполнение принимает только `contract: 2` и `registration: prospective`.
Пример малого протокола: [проверка очереди](experiments/2026-10-17-queue-probe-protocol.json).
Дополнительные обязательные поля:

- `case_faces`: для каждого случая полный список граней; каждая содержит
  `field`, `kind`, `axis`, `side` (`lower`/`upper`). Во всех состояниях проверяется
  точное совпадение множества идентификаторов без пропусков и дублей.
- `network`: полная ожидаемая конфигурация сети после применения ветви опыта.
  Исполнитель проверяет её до обучения; результат сохраняет её для сборщика.
  Различные архитектуры требуют отдельного режима сравнения, не отключения проверки.
- `environment_requirements`: точные `torch`, `cuda_runtime`, `default_dtype`,
  `float32_matmul_precision`, `cuda_matmul_allow_tf32`, `cudnn_allow_tf32`.
  Фактическая среда проверяется при сборе, значения по умолчанию не угадываются.

Один отчёт соответствует одному случаю; `reports` упорядочен как `case_limits`.
Путь каждого отчёта заканчивается `/report.json`. Ожидаемые случаи, seed и ветви
перечислены полностью, бюджет каждой пары одинаков. Старые ретроспективные
данные не превращаются в перспективные одной сменой номера контракта.

## Приёмка доказательств

Сборщик принимает текущий контракт отчёта сходимости 3, только `completed`.
Проверяет весь бюджет, пороги, среду и SHA, точную матрицу, полноту расписания
состояний, конечность/неотрицательность метрик, неубывание времени. Каждая пара
должна иметь одинаковые отпечатки начальных весов и фиксированных PDE-точек,
а также одинаковый размер и режим замера предсказания.

Независимая оценка должна сообщать `eager` / `general` / `autograd`, в том числе
для аналитического кандидата. Заявленное аналитическое исполнение должно
соответствовать фактическому правилу производных. Дефект начальных и граничных
условий проверяется во всех сохранённых состояниях, а не только в последнем.
Пропущенная метрика, NaN, отсутствующая грань в виде пустого списка или
несопоставимые веса — ошибка данных, а не успешный опыт.

Происхождение файлов сохраняется через SHA-256 исходных отчётов и манифеста.
Это контроль связи с исходными файлами, **не электронная подпись**. Сохранённые
флаги прохождения и пересечения заново вычисляются при сравнении.

Для `prospective` требуется явно чистый рабочий каталог в отчётной среде.
В 008/009 среда записала `working_tree_dirty: true`: импорт сохраняет этот факт
и требует отдельной проверки происхождения. Один SHA не доказывает отсутствие
изменений исходников; нельзя скрывать эту оговорку под успешными численными
критериями. Будущий исполнитель должен работать из неизменяемого Git-снимка.

## Математический смысл критериев

Пусть m — одна метрика, A — контроль, B — кандидат, ε — абсолютный целевой порог,
α — зарегистрированный множитель допуска. Сохранение качества проверяется так:

$$
m_B \le \max(\alpha m_A,\varepsilon).
$$

Абсолютное попадание в целевую точность — другое утверждение:

$$
m_B\le\varepsilon.
$$

Поэтому два одинаково неточных метода способны пройти критерий сохранения
качества и одновременно не решить задачу с требуемой точностью. В выводе эти
события разделены. Для подтверждения точности нужны два соседних сохранённых
состояния, прошедших все метрики. Первое пересечение даёт интервал между
контрольными измерениями; линейная интерполяция запрещена. Если уже первое
состояние прошло порог, интервал помечается `left_censored`.

Время обучения включает предыдущие контрольные сохранения; независимая оценка
не включается. Отношение времени считается отдельно для каждой пары, затем
медиана по seed; нельзя подменять его отношением двух независимо взятых медиан.
Это время фиксированного бюджета. Время до точности выводится отдельно через
интервалы и момент подтверждения. Быстрый неточный метод не объявляется
ускорением достижения точности.

Граничная ошибка температуры не равна дефекту оператора Неймана. Сборщик
использует `boundary_operators[*].max_error` для физических ограничений.
Дискретная независимая проверка не доказывает непрерывной оценки ошибки PDE.
Полные математические ограничения: [контекст агента](agent-research-context.md).

## Хранение и ограничения первого этапа

`evidence.json` нужен для последующего машинного сравнения и хранится в
игнорируемом `numerical-reports`, не копируется в Git по умолчанию. В нём только
метрики контрольных состояний, без полных временных профилей и весов. В Git
попадают небольшие CSV/сводки и необходимые манифесты. Математические Markdown
не сокращаются ради объёма данных. Большие журналы не отправляются в stdout.

Контракт 1 по-прежнему позволяет локально анализировать прежние отчёты. Только
контракт 2 фиксирует геометрический список, архитектуру и точность. Сборщик не
проверяет веса повторным обучением и не доказывает непрерывную точность решения.

## Удалённый исполнитель: жизненный цикл

Существующие `.gpu-jobs/gpu.lock`, `ProcessTree`, архиватор и окружение
переиспользованы из `gpu_worker.py`. Старый API `gpu_jobs.py` сохраняется для
прежних `benchmark_solutions`; новая очередь не имеет второго GPU-замка.

`submit` принимает **commit протокола**, а поле `revision` внутри протокола
задаёт **commit обучения**. Это разные объекты: файл не может содержать SHA
собственного ещё не созданного коммита. Оба объекта должны быть достижимы из
полученных `origin`-веток. На Windows `git show` читает точные байты протокола,
SHA-256 сравнивается с запросом до создания снимка. Сам протокол и запрос
сохраняются рядом с архивом, отдельно от распакованного исходного кода.

Снимок из `git archive` проверяется побайтово по архиву, включая отсутствие
лишних файлов; проверка повторяется перед запуском и перед каждым случаем.
`-B`/`PYTHONDONTWRITEBYTECODE` исключают запись bytecode в снимок. Результаты,
веса, журналы и все кэши находятся рядом, внутри `.gpu-jobs/ID`.
Это защита от случайного изменения; не криптографическая изоляция от пользователя,
имеющего права изменять весь проект и архив одновременно.

Рабочий процесс создаётся через Windows `CreateProcess` с флагами
`DETACHED_PROCESS | CREATE_NEW_PROCESS_GROUP | CREATE_BREAKAWAY_FROM_JOB`.
Он переживает выход SSH без службы и планировщика. Если политика Job Object
на другой машине запрещает отделение, операция должна явно отказать;
повышение прав и обход политики не выполняются. WMI был проверен на этом ПК,
но вернул отказ в доступе, поэтому от него отказались.

До обучения дочерний процесс ждёт разрешающий файл: владелец сначала помещает
его в `ProcessTree`, затем разрешает исполнение. Это исключает промежуток, когда
обучение уже создало потомков, а управление деревом ещё не установлено.
Таймаут относится к выполнению после получения GPU, не ко времени ожидания.
Отмена проверяется и при ожидании общего замка. Не требуется перезапускать SSH,
чтобы процесс продолжал считать или публиковал короткий прогресс.

ID ограничен 16 безопасными символами из-за длины путей Windows. Запрос с тем же
ID и теми же параметрами идемпотентен; с другими параметрами отклоняется.
Отдельные одноразовые отметки подготовки запуска и исполнения исключают второй
запуск. Если SSH оборвался в неоднозначный момент, повтор не создаёт новую копию:
`unknown` требует проверки. Автоматического возобновления частично обученной
серии нет — оно могло бы изменить историю оптимизатора и смысл опыта.

Для живого процесса проверяется не только PID, но и время его создания через
`GetProcessTimes`: повторно использованный PID не принимается за владельца.
`queued/running/completed/failed/timed_out/cancelled/unknown` — состояния процесса.
При `unknown` нельзя считать обучение ни законченным, ни безопасно отменённым.
Запрос отмены в таком случае не гарантирует завершения осиротевшего потомка;
нужна явная проверка владельца. Таймштамп показывает последнее подтверждение,
прогресс хранится отдельным небольшим файлом, а не извлекается из больших отчётов.

`--probe` выполняет трёхсекундный процесс стандартной библиотеки без Torch.
Он проверяет жизненный цикл; `collect` не выдаёт его за научный результат.
Для проверки всей цепочки нужен отдельный минимальный реальный протокол.
Никакое `completed` не заменяет проверки полноты, точности и происхождения.

Низкоуровневые контракты Windows:
[флаги создания процесса](https://learn.microsoft.com/en-us/windows/win32/procthread/process-creation-flags),
[идентификация временем создания](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-getprocesstimes).

### Исходные критерии TASK-28

Цель — заменить временные PowerShell/Python-рецепты, используя существующие
`gpu_jobs.py`, `gpu_worker.py`, `convergence_processes`, без второго механизма
блокировки GPU. Список критериев сохранён для сверки реализации; подробнее см. выше:

1. `submit` принимает заранее опубликованный протокол; фиксирует его хеш и
   точный опубликованный SHA до старта. Нельзя молча тестировать новый HEAD.
2. Отдельный неизменяемый снимок внутри `C:\Projects\pinn-runner`; запуск из
   обязательного рабочего каталога. Все кэши и временные файлы внутри проекта.
3. Идемпотентный ID: повторный запрос не запускает вторую копию. Одна GPU-очередь,
   явные состояния `queued/running/completed/failed/timed_out/unknown`.
   Обрыв SSH не считается автоматически ни успехом, ни остановкой обучения.
4. Длительное обучение переживает завершение управляющего запроса; статус
   содержит время последнего подтверждения и прогресс без чтения полных отчётов.
5. `collect --remote` сначала валидирует данные на Windows, затем передаёт
   компактные результаты. Сырые данные остаются доступными по явному запросу.
6. Таймаут и отмена завершают дерево процессов; восстановление проверяет
   состояние владельца блокировки и процесса, а не только давность файла.
7. Статус процесса, полнота серии и качество решения — разные поля. Общий
   `completed` никогда не означает автоматически «решение верно».
8. Контракт фиксирует ожидаемые грани и дополнительные параметры точности,
   архитектуры/конфигурации. Сравнение разных представлений может иметь разные
   начальные веса: для него нужен отдельный явно обоснованный режим, не обход
   текущей проверки одинаковых отпечатков.
9. Тесты на Mac используют поддельный транспорт, обрыв связи, повреждённый файл,
   повторный ID, неверный каталог и частичный результат. Затем короткая реальная
   Windows-проверка транспорта, не новое длительное обучение.

Не делать в этом этапе: новую серверную платформу, веб-интерфейс, обновление
Torch, автоматическое изменение математических ограничений или основных настроек.

Ограничение текущего исполнителя: используется реестр случаев и CLI сходимости
тепловых задач. Добавление нового PDE требует отдельного эталонного случая и
независимой оценки; произвольный файл команд в протоколе не исполняется.
Неизвестный владелец не завершается по одному PID; автоматического удаления
каталогов задач, получения повышенных прав или перезапуска такой задачи нет.

### Целостность пакета и диагностика

После TASK-29 `compare` проверяет завершающий `bundle.json` и SHA-256 трёх
файлов пакета. Частично записанный или изменённый пакет не принимается. Старые
пакеты без завершающей записи пересобираются в новую папку из прежних отчётов,
без обучения. Не дописывать маркер вручную.

`diagnose` по умолчанию не читает журналы. Явный хвост ограничен байтами до
чтения и строками после декодирования. Локальная копия не используется для
проверки Windows-PID на Mac. Повреждённые метаданные дают `unknown`; однозначный
отказ до создания процесса сохраняется как `failed`. Подробности, ограничения
и критерии: `docs/research-diagnostics.md`. Математические критерии не изменены.

### План до обращения к GPU

`plan --manifest protocol.json [--details]` проверяет исполнимость протокола
без Torch, сети и записи файлов. Показывает матрицу и бюджет, отклоняет
неизвестные случаи и несовместимые варианты. Та же проверка применяется в
`submit`, подготовке Windows-очереди и исполнителе. Каталог относится к текущей
версии инструмента; произвольный старый SHA он не сертифицирует.
Подробные требования, математические ограничения и смысл бюджета:
`docs/research-planning.md`.

### Поиск текущей задачи

`tasks [--status STATUS] [--limit 5] [--skip 0]` возвращает страницу текущих
карточек со ссылками на требования, без истории. По умолчанию Done и Deferred
исключены; `next_skip` задаёт продолжение. Поле готовности доски не является
разрешением начать работу. Контракт: `docs/research-task-index.md`.

### Опыт плотности с бюджетом времени

Для TASK-21 контракт 2 допускает необязательный объект `density`:
`training_seconds`, `snapshot_seconds`, `sampling: nested_uniform`, `prefix_points`.
В этом режиме ветви и строки `expected_trials` дополнительно содержат положительный
`points_override`; общий `report_parameters.points_override` равен null.
Все остальные поля ветвей обязаны совпадать, кандидат содержит больше точек,
а `prefix_points` совпадает с числом точек контроля. Прежний режим неизменен.

Adam и L-BFGS имеют общий бюджет времени; `adam_steps` и последнее значение
`lbfgs_snapshots` становятся защитными верхними пределами, а не равным объёмом
работы. Сохранения делаются по времени после Adam; полный список шагов различается
между ветвями. `plan` помечает такой бюджет `wall_time_with_step_caps`, возвращает
`saved_states_total: null` и верхнюю границу числа сохраняемых состояний.

Сбор проверяет завершение временного бюджета, монотонность состояний, границы
шагов, точное совпадение параметров опыта, отпечатки общей начальной модели
и вложенного префикса. Состояния после срока не подтверждают точность. Помимо
прежних метрик сохраняются число точек, счётчики PDE, превышение бюджета и
пиковая память. `comparison_passed` в режиме плотности означает прохождение
всеми кандидатами подтверждённых абсолютных порогов и физических ограничений;
поля обычного парного сравнения остаются диагностическими. Это не доказательство
ускорения или превосходства над контролем. Протокол и математические предпосылки:
[density-neumann-protocol-2026-10-17.md](density-neumann-protocol-2026-10-17.md).

### Дополнительные компактные измерения

Для обычных серий с фиксированными шагами сборщик также сохраняет уже измеренные
`peak_allocated_bytes`, `peak_reserved_bytes`, время сохранений/подготовки/оценки
и процесса, если эти поля есть в исходном отчёте. В срезах сохраняются счётчики
PDE для Adam и L-BFGS. Отсутствие поля в старом отчёте не подменяется нулём;
присутствующие значения проверяются на конечность и неотрицательность.
Новые отчёты сходимости включают `worst_time_relative_l2` в компактные метрики
при обоих режимах бюджета. Это дополнение измерений, без изменения обучения.

### Ограниченный нативный профиль: контракт 3

`plan/submit/status/cancel/collect/compare` также поддерживают отдельный
`contract: 3`, `kind: frozen-profile`, `registration: prospective`.
Это не обучение и не совместимый с ним численный отчёт. Поля: `revision`,
`case` (только два зарегистрированных контроля Неймана 2D), `trial` (относительно
Windows-корня, внутри `.gpu-jobs`), `weights` (одно имя файла),
`weights_sha256`, `config_sha256`, `points` (1..4096) и точный прежний
`environment_requirements` FP32/TF32-off. Неизвестные поля отклоняются.

Исполнитель фиксирован: установленный Nsight Systems 2023.1.2, два отдельных
процесса обычного/аналитического правила, без обновления весов, sampling и
переключений CPU. Использует те же блокировку, снимок, таймаут и дерево процессов.
Сбор сверяет отпечатки сырых файлов на Windows, передаёт компактную сводку;
пакет сохраняет `bundle.json` и проверяемые SHA256. `comparison_passed` означает
только успешный захват событий CUDA обеих ветвей при сохранённых источниках.
Даже true **не означает** точность PDE или ускорение. Отрицательная диагностика
профилировщика сохраняется, если очередь сама завершила сбор отчёта.
Математика и заранее заданный критерий: `native-profile-protocol-2026-10-18.md`.

### Замороженные измерения без профилировщика: контракт 4

`contract: 4`, `kind: frozen-timing` фиксирует до запуска источники
`case/seed/trial/weights/weights_sha256/config_sha256`, `revision`, точную
среду FP32/TF32-off и числовой бюджет. Только четыре контроля Неймана 2D/3D,
до восьми уникальных источников, три пары на источник, 1024 точки невязки,
8193 точки предсказания, пакеты128/2048, девять блоков 6с и 0,75с соответственно.
Все остальные значения и неизвестные поля отвергаются. Свободных команд нет.
Те же `plan/submit/status/cancel/collect/compare` и прежняя блокировка GPU.

Контроль источников и численные допуски обязательны. В пакете остаются сырые
числа вызовов/длительностей блоков, медианы пересчитываются. Принятие сравнивает
пары на одинаковых весах/точках и отдельно возвращает отсутствие утверждения
о точности PDE. Свежий процесс не считается полным файловым cold end-to-end.
Полный протокол: `frozen-timing-protocol-2026-10-18.md`.

## Контроль распределителя Torch, contract7

`allocation-profile` — фиксированная пара правил на сохранённом полиноме2D/1024
точках, без шагов оптимизатора. Источники проверяются как у contract3; пять

Это диагностика памяти, не CUDA kernel timing или новый fast path. Отсутствие

Протокол: `allocation-profile-protocol-2026-10-18.md`.

## Публичное холодное предсказание, contract8

`public-prediction` — фиксированная сохранённая модель полинома3D,12 новых
CLI-процессов, batch128/2048,17³×31 значений. Часы включают интерпретатор,
подготовку модели, чтение, расчёт и MAT; ОС/драйвер не сбрасываются.
Контейнер из исследовательского state_dict сравнивается с исходными тензорами,
все процессы проверяют точность/устройство и дают точные парные поля.

Протокол: `public-prediction-protocol-2026-10-18.md`.

### Сравнение представлений коэффициента в контракте2

Опциональный объект `physics` включает ровно физические случаи
`heat_conductivity_beta0`/`heat_conductivity_beta1`, зарегистрированные в каталоге.
Каждая ветвь и ожидаемая траектория дополнительно задают
`coefficient_representation`: formula/table. Внутри пары все пять прежних полей
исполнения одинаковы; плотность точек одновременно не варьируется.
Обязательны также `worst_time_relative_l2` и `physical_flux_max` в `case_limits`.

Этот режим оценивает абсолютную точность. В `comparison` остаются
baseline/candidate/quality_factor, временных gates нет. Итог требует финальной
точности обеих ветвей, физических условий и парного качества; времена
сохраняются, `timing_passed=null`, `comparison_purpose=absolute_accuracy`.
Начальные параметры сети сравниваются отдельно от физических буферов.
Отчёты обязаны содержать `physics`, `problem_source_sha256` и
`initial_parameters_sha256`; подмена beta, исходника или параметров отклоняется.
Прежние протоколы без `physics` сохраняют строгую проверку полного состояния.

Постановка и критерий окончания:
[перспективный протокол](variable-conductivity-convergence-protocol-2026-10-19.md).

Коэффициентные случаи создают самостоятельный источник через исследовательскую
сходимость с явным `coefficient_representation`. Общий CLI `benchmark_solutions`
такого параметра пока не содержит; непосредственный запрос `case.source`
у этих случаев выдаёт явную ошибку подготовки, защищая от выбора неверного beta.
