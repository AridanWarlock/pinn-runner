# TASK-21: файловая приёмка выбранного правила на Windows

## Вопрос и ограничение

Сохраняются ли файловые контракты выбранного `neumann_analytic` на целевом
Windows CUDA-стеке: обучение, сохранение, загрузка, предсказание на другой
сетке и дальнейшее обучение весов? Это обязательная приёмка существующего
правила, не новый способ оптимизации и не исследование точности с нуля.

Используется общий режим `numerical-acceptance`, contract6. Разрешён второй
фиксированный набор — `tests/integration/test_neumann_feature_runner.py`,
ровно шесть заранее перечисленных nodeid. Первый геометрический набор и
его старые протоколы остаются совместимыми. Произвольные команды/pytest-файлы
не разрешаются. SHA кода, канонический SHA256 теста и список сценариев
публикуются отдельным перспективным JSON до запуска.

## Матрица

| Случай | Представление | Исполнение |
|---|---|---|
| Полином1D | Косинусное Неймана | eager, контроль прежнего контракта |
| Полином1D | Полиномиальное Неймана | neumann_analytic |
| Полином3D | Полиномиальное Неймана | eager |
| Полином3D | Полиномиальное Неймана | neumann_analytic |
| Мода2D | Полиномиальное Неймана | eager |
| Мода2D | Полиномиальное Неймана | neumann_analytic |

Начальное состояние seed19, сеть4×4. Обычный fit:3 шага Adam и2 внешних
шага L-BFGS. Точки PDE —7 LHS, пакет7; начальная сетка по3 узла на ось,
временных узлов3. Предсказание меняет пространственную сетку на4 узла на ось,
сохраняя физические интервалы. Поля должны быть конечными и иметь точный
размер. Для аналитических сценариев тот же checkpoint дополнительно
предсказывается с `eager`; массивы MAT обязаны совпасть точно.

После обычного retrain проверяется отказ при подмене представления на
`identity`/`robin_grouped`: несовместимая сохранённая модель не принимается
под видом прежней физической модели.

## Независимая проверка фактической загрузки весов

Одного успешного кода возврата retrain мало: ошибочный запуск с нуля тоже
мог бы завершиться успешно. Поэтому после первоначального сохранения есть
отдельный запуск retrain с одним шагом Adam, нулевым weight decay,
learning rate1e-300 и без L-BFGS. Эта положительная скорость обучения
допустима текущим Reader, но обновление параметров FP32 округляется в ноль.
Это только диагностический режим теста, не предлагаемая настройка обучения.

Для FP32 минимальное положительное субнормальное число равно:

$$
\delta_{\min}=2^{-149}.
$$

Масштаб1e-300 намного меньше разрешения FP32 даже с запасом на нормировку
конечных градиентов Adam и его положительное epsilon. Само доказательство
контракта — **побитовое сравнение всех тензоров state_dict** после такого
запуска с исходной сохранённой моделью. Если checkpoint проигнорирован,
исходная случайная сеть этому сравнению не соответствует.

Затем конфигурация обычного обучения полностью восстанавливается.
Каждый сценарий содержит два обычных fit и один диагностический:
всего12 обычных fit по3 Adam+2 L-BFGS и6 диагностических fit по1 Adam.
Это проверяет загрузку и дальнейшее обучение **весов**. Восстановление
истории Adam/L-BFGS при публичном retrain не заявляется: текущий контракт
запускает новую стадию оптимизации на загруженных весах.

## Рабочий каталог и точность

Каждый subprocess остаётся в `C:\Projects\pinn-runner`; до запуска
проверяются текущий каталог и принадлежность абсолютного пути `run.py`
проекту. `run.py` берётся из закреплённого снимка. Явный загрузчик сохраняет
обычные CLI-аргументы, выбирает pinned-каталог импортов и выключает TF32
для matmul/cudnn в каждом дочернем процессе. Публичный решатель не меняется.
Проверены реальные argv/импорты/флаги отдельным CPU-тестом загрузчика.

Целевая среда приёмки прежняя: RTX4070Ti, Torch2.1.0+cu118, CUDA11.8,
FP32. Файлы/кеши/временные каталоги находятся внутри проекта. Канонический
SHA теста учитывает только LF/CRLF; сырые байты и полный снимок проверяются
до/после. Общая GPU-блокировка и Windows Job Object сохраняются.

## Критерий окончания

Общий таймаут900с без автоматического продления, отдельный CLI-вызов имеет
существующий лимит90с. Успех — все6 сценариев и18 фаз setup/call/teardown
успешны, оба вида точных сравнений пройдены, несовместимое представление
отвергнуто; затем штатные collect и compare в новом локальном пакете.
Пропуски, xfail/xpass и ошибки teardown не считаются успехом.
Отрицательный результат сохраняется. Численные допуски/точность не подбираются
по результату. Производительность и достижение точности этим набором не оцениваются.
