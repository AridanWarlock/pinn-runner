# Короткая проверка времени до точности

`scripts/benchmark_time_to_quality.py --output numerical-reports/time-quality-001`
запускается только на Windows CUDA из обязательной директории проекта.

Это screening для heat3d: seed 1234/19, eager/product_rule, 3000 шагов Adam,
затем 300 внешних шагов L-BFGS. Порядок backend обращается на втором seed.
Состояния модели сохраняются после 0/25/50/100/150/200/300 шагов L-BFGS.
Оптимизатор не пересоздаётся между точками; objective фиксируется один раз.
Никакой аналитической оценки или ранней остановки во время обучения нет.

Пороги зафиксированы до запуска: общий relative L2 <= 0.001, final relative
L2 <= 0.002, независимый physical-autograd PDE RMSE <= 0.005 одновременно.
Это более строгая исследовательская цель, отдельная от существующих acceptance
порогов. Требуются две соседние сохранённые точки с прохождением. Первый успех
даёт верхнюю границу наблюдаемого времени, предыдущая точка — нижнюю; точный
момент между ними неизвестен. При успехе уже после Adam нижняя граница
неизвестна (left-censored); при отсутствии пары успехов crossing не подтверждён.
Две соседние точки не доказывают сохранение точности навсегда.

Время измеряется от начала fit, включает подготовку fixed objective и предыдущие
сохранения snapshot, но не построение factory и аналитическую оценку. CUDA
синхронизируется перед отметкой времени. Суммарная стоимость сохранения
snapshot отражена отдельно. Это время данного benchmark, а не cold public
runner latency. Измеряется пересечение только на стадии L-BFGS: промежуточных
Adam checkpoint нет. Этот ограниченный протокол не оценивает точный первый
момент достижения порога во всём обучении.

После полного обучения модели восстанавливаются для оценки на eager backend.
Проверка решения использует обычную аналитическую сетку heat3d; PDE — отдельные
2048 случайных точек с seed 20261013, через полную AD физических полей.
Snapshot содержат только state_dict модели и предназначены для оценки, а не
возобновления обучения. Сохранённый config в каждой trial-директории в итоге
описывает evaluation grid; training recipe зафиксирован в этом скрипте.

Быстрый набор `python scripts/check.py` и профильные тесты достаточны при изменении
этого отдельного инструмента. Production training/config/checkpoint контракт
не изменён. Полная численная матрица нужна перед решением о defaults; два seed
не заменяют её и не позволяют надёжно оценить статистическую вариативность.

## Результат RTX 4070 Ti, 2026-10-13

Revision `4bcd54c`, Torch 2.1.0+cu118, FP32, TF32 off. Все четыре trial
завершились; всего 12000 Adam и 1200 внешних L-BFGS шагов. Полная прежняя
матрица из 30 обучений не повторялась. Суммарное измеренное обучение — 177.69 s;
оценка checkpoint и загрузка Python в эту сумму не входят.

| Seed | Backend | Последняя неудачная точка, s | Первая успешная, s | Подтверждение, s | LB шаг первой успешной |
|---|---|---:|---:|---:|---:|
| 1234 | eager | 42.083 | 43.617 | 46.659 | 200 |
| 1234 | product_rule | 40.661 | 42.053 | 44.754 | 200 |
| 19 | eager | 41.536 | 43.051 | 46.100 | 200 |
| 19 | product_rule | 34.781 | 36.130 | 37.475 | 150 |

Верхние границы наблюдаемого crossing уменьшились на 3.59% и 16.08%; это
не точная оценка изменения истинного времени пересечения. Интервалы seed1234
разделены лишь 0.030 s: дискретность checkpoint и вариация wall time не позволяют
считать результат надёжным доказательством величины выигрыша. У seed19 интервалы
разнесены существенно, а число LB шагов до первого наблюдаемого успеха меньше.
Это согласуется с пользой fast path, но двух seed мало для смены defaults.
При 300 шагах финальный L2 у product_rule немного хуже в обеих парах:
0.1143% против 0.1128% и 0.1112% против 0.1045%. Ускорение не означает
покадрового улучшения точности FP32.

Сохранение семи snapshot заняло 8.27–10.03 ms на trial, менее 0.03% измеренного
обучения. Независимая проверка использовала eager AD; все четыре backend/seed
прошли одновременно все три исследовательских порога в двух соседних точках.
Данных об inference latency этот инструмент не добавляет: prediction здесь
используется только для оценки качества, без отдельного timing.

В environment `working_tree_dirty=true`: на Windows остались старые untracked
каталоги pytest и установщик Python. Отдельный `git diff --exit-code HEAD --
run.py pinnstorch benchmarks scripts` подтвердил отсутствие изменений исходников.
Файлы пользователя не изменялись. SSH закрылся после завершения.

Проверки: Ruff lint/format, strict mypy основного набора (52 файла), отдельно
strict mypy benchmark (1 файл); быстрые CPU **244 passed, 20 e2e deselected**.
Полный CPU и полная CUDA acceptance-матрица в этом блоке не запускались:
production solver не менялся. Новые два теста проверяют соседнее подтверждение,
правую/левую цензуру и отсутствие интерполяции.

Сырые метрики: [JSON](experiments/2026-10-13-time-quality-screening.json).
Windows snapshots/log: `numerical-reports/time-quality-001` и
`numerical-reports/time-quality-001.log`. Следующий шаг — TASK-22 ConstraintPlan;
TASK-21 остаётся открытой из-за неполного CUDA kernel profiling и ограниченного
screening времени до точности.

## Обобщение измерителя, 15 октября 2026

Из скрипта убраны предположения о трёх координатах, единичном кубе,
нулевом Дирихле и единственной паре способов вычисления. План, варианты,
обучение с промежуточными сохранениями и независимая оценка выделены в
`benchmarks/convergence.py`. CLI теперь задаёт тепловую задачу, состояния
генератора, ограничения, способы проекции/продолжения/обратного прохода,
число PDE-точек, шаги Adam и моменты сохранения на стадии L-BFGS.

Промежуточные веса сохраняются **без обращения к эталону**. Только после
окончания всех шагов конкретного опыта вычисляются ошибки и время достижения
заранее заданных порогов. Это прямо проверяется CPU-тестом с запретом обращения
к аналитическому ответу до окончания обучения. Оценка PDE дифференцирует
физическое поле обычным способом, независимо от ускорителя производных.

Время записано перед сохранением текущей модели и включает расходы предыдущих
сохранений. Их суммарная стоимость публикуется отдельно; она не вычитается
молча из времени достижения точности. Для подтверждения нужны два соседних
успешных наблюдения. Если самый первый срез после Adam уже успешен, истинное
время достижения до него неизвестно: результат помечается `left_censored`.
Точки внутри Adam пока не сохраняются — нельзя обещать измерение первого
достижения за весь процесс обучения. Подробные временные ошибки, счётчики
посещений PDE-точек, тёплое предсказание и память также включены в отчёт.

Пример протокола обратного прохода (только Windows CUDA):

```powershell
.\.venv\Scripts\python.exe scripts/benchmark_time_to_quality.py `
  --output numerical-reports/backward-convergence-001 `
  --case heat_neumann3d --seeds 19 1234 `
  --constraints hard_initial_robin --hard-execution robin_grouped `
  --hard-lifting recursive --backward all parameters --points 2048 `
  --steps 2000 --snapshots 0 25 50 100 150 `
  --relative-l2 0.001 --final-relative-l2 0.002 --pde-rmse 0.015
```

Эти пороги времени достижения отдельны от общих строгих проверок решения.
Их нужно зафиксировать до запуска и не подгонять по увиденным срезам.

Время срезов отсчитывается от начала `fit`; подготовка модели/выборки и оценка
после обучения учитываются отдельными `setup_seconds`, `evaluation_seconds`,
`trial_wall_seconds`. Это не холодный запуск нового процесса на каждый срез.
При немонотонной ошибке между наблюдениями могли быть незамеченные пересечения.
Поэтому `lower_seconds` — время предыдущего неуспешного наблюдения перед
подтверждённым переходом, а не доказанная нижняя граница самого первого
пересечения за всю непрерывную траекторию.

### Как читать предсказание в опыте со срезами

В отчётах схемы 2 итоговое тёплое предсказание измерялось объектом
`SnapshotEvaluation`: это **независимый контрольный `eager`**, сохраняющий
выбранное продолжение. Входы уже на GPU, перенос результата на CPU в это время
не включён. Измерение не является задержкой обучавшего `robin_grouped` или
`product_rule`; напрямую сравнивать его с их производственной задержкой нельзя.
Для фактического пути предсказания служат основной `benchmark_solutions.py`
и его `warm_prediction_seconds`. Разные исполнительные пути объясняют,
почему одинаковые веса могут иметь разные времена в этих двух инструментах.

В прежнем CLI несколько вариантов по умолчанию обучались последовательно в одном
процессе. Первый опыт 16 октября обнаружил небольшое различие FP32-траекторий,
не наблюдавшееся в основной матрице отдельных процессов. Поэтому для проверки
режима в условиях одноразового runner использовать отдельный вызов CLI
с одним состоянием и одним вариантом на процесс. Набор порогов не менять.
Это не доказательство конкретной причины внутри CUDA; диагностический протокол:
[изолированный повтор](experiments/2026-10-16-backward-isolation-protocol.json).


## Изолированные процессы и схема 3, 16 октября 2026

Теперь обычный вызов CLI создаёт **отдельный процесс Python на каждый опыт**
(состояние генератора × вариант). Координатор не опрашивает и не инициализирует
CUDA. Порядок вариантов обращается для каждого следующего состояния генератора.
Явный `--shared-process` оставлен для диагностики; если вариант всего один,
дочерний отчёт помечен `single_trial`, иначе — `shared_process`.

Общий отчёт имеет `contract: 3`, `execution_lifecycle: isolated_trials`.
Он дополняется после каждого успешно проверенного дочернего отчёта через
временный файл и атомарную замену. При аварии дочернего процесса уже собранные
данные сохраняются со статусом `running`; такой отчёт не считается завершённым.
Несовпадение протокола, состояния генератора, варианта, ревизии исходников или
описания окружения останавливает сбор. Каталог результата должен быть новым.
Изоляция не доказывает абсолютную воспроизводимость CUDA и не защищает от
внешнего изменения незакоммиченного исходника между проверками. Для численной
серии нужна чистая зафиксированная ревизия без обновлений во время опытов.

В каждой записи `process_seconds` включает запуск дочернего Python, подготовку,
обучение, оценку и завершение. `training_seconds_with_snapshots` по-прежнему
относится только к обучению и сохранениям. Эти интервалы нельзя смешивать при
сравнении времени до точности. `study_seconds` относится ко всей последовательной
серии, включая работу координатора.

В схеме 3 `warm_prediction_seconds` измеряет **обученный исполнитель** на последнем
наборе весов, а `prediction_execution` записывает его имя. Отдельное поле
`control_prediction_performance` содержит время независимого `eager`, который
использовался для проверки физических производных; его имя указано в
`control_prediction_execution`. Входы уже находятся на устройстве, перенос
результата на CPU не входит в оба измерения. Старые отчёты схемы 2 не переименованы:
их прежние числа остаются временем контрольного `eager`.

Текущая пятисостоянийная серия была начата на `c24e0f2` до этого изменения,
но уже запускала **по одному варианту и одному состоянию на отдельный вызов
Python**. Её девять срезов и пороги зафиксированы в
[протоколе](experiments/2026-10-16-convergence-five-protocol.json).
Не следует выдавать её старое измерение предсказания за скорость обученного
исполнителя или смешивать бюджет 200 шагов L-BFGS с прежним бюджетом 150.
