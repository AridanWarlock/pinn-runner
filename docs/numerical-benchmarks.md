# Численная приёмка PINN

Проверка успешного запуска не равна проверке решения. Здесь проверяем публичный
`run.py`: настоящий train, final checkpoint, predict на другой сетке и сравнение
с аналитикой. Эталон не передаётся в loss; `data.mat` не нужен.

## Задачи

Области: x (и y) в [0,1], t в [0,0.5]. Все задачи имеют одно поле u.

| Задача | PDE | Аналитическое решение | Условия |
|---|---|---|---|
| heat2d | u_t − 0.1 Δu = 0 | sin(πx)sin(πy)exp(−0.2π²t) | Начальный синус, Дирихле 0 на четырёх гранях |
| advection | u_t + u_x = 0 | sin(π(x−t)) | Начальный sin(πx), вход x=0: −sin(πt); выход x=1 без условия |
| burgers | u_t + u u_x − 0.1 u_xx = f(x,t) | exp(−t)sin(πx) | Начальный sin(πx), Дирихле 0 на концах |

Для Бюргерса берём v=exp(−t)sin(πx), затем задаём известный источник
f=(−1+0.1π²)v + v πexp(−t)cos(πx). Это manufactured solution: источник выбран
так, чтобы сложная PDE имела точное решение. Он является частью уравнения,
а не обучающими наблюдениями. Подход позволяет позже добавить волновые,
реакционно-диффузионные, многополевые задачи и неоднородные коэффициенты.
[Описание метода в NASA Code Verification Testing Practices](https://www.nas.nasa.gov/assets/nas/pdf/papers/NASA-TP-2016-219422_and_JANNAF-GL-2016-0001.pdf).

Быстрые CPU-тесты сначала проверяют, что аналитические поля удовлетворяют
реализованным PDE, IC и BC. NumPy-формулы оценки отделены от Torch-операторов
обучения. Это уменьшает риск принять неверный источник/знак за ошибку сети.

## Измерения

- Общая относительная L2 = ||u_PINN − u_exact||₂ / ||u_exact||₂ по всей сетке.
- RMSE и максимальная абсолютная ошибка.
- RMSE на t=0 и на заданных границах (для переноса — только вход).
- Относительная L2 на последнем временном срезе.
- RMSE невязки PDE на 2048 новых случайных точках, с отдельным seed 20261013.
- Время train-процесса, включая его запуск, подготовку и запись checkpoints.

Оценочная сетка имеет 41 точку на пространственную ось и 31 по времени; обучение
использует 16 точек на ось для IC/BC, 11 по времени и 1024 LHS-точки PDE.
Граничные точки/начальный срез закономерно пересекаются, но внутренние точки и
набор проверки PDE независимы. Метрики оценивают дискретную сетку, не непрерывную
норму и не строгое доказательство точности между точками.

Пока задачи без параметров, геометрия прямоугольная, решение гладкое, только
float32. Эти три задачи не подтверждают корректность всех возможных PDE,
разрывов, mixed precision и больших 3D-задач. Набор будем расширять отдельно.

## Запуск Windows (PowerShell, строго из C:\Projects\pinn-runner)

Окружение и ограничения SSH описаны в AGENTS.md. До команды задайте TEMP/TMP,
кеши внутри проекта, затем выполните:

```powershell
& '.\.venv\Scripts\python.exe' scripts/benchmark_solutions.py --output-dir numerical-reports\standard-001
```

По умолчанию CUDA, три задачи, seeds 1234 и 4321, по 3000 Adam-шагов, сеть
32×32×32, learning_rate=0.001, batch_size=128. `reference` увеличивает бюджет до
6000 шагов, остальные настройки сохраняются:

```powershell
& '.\.venv\Scripts\python.exe' scripts/benchmark_solutions.py --profile reference --output-dir numerical-reports\reference-001
```

Каждый output-dir должен быть новым: скрипт не перезаписывает прошлую приёмку.
Для целевого расследования можно выбрать `--cases advection` и `--seeds 1234`,
а `--steps` задаёт отдельный бюджет, который фиксируется в fingerprint.
На Mac разрешён только короткий CPU smoke, без проверки сходимости:

```sh
python scripts/benchmark_solutions.py --device cpu --profile smoke --seeds 1234 --output-dir /tmp/pinn-smoke-new
```

`smoke_passed` означает работоспособность маршрута за три шага, **не** хорошее
решение. Длинные численные проверки выполняем на Windows CUDA.

## Приёмка и регрессии

Начальные требования к этим нормированным задачам: общая relative L2 ≤ 5%,
max_error ≤ 0.15, RMSE PDE ≤ 0.1, RMSE IC и BC ≤ 0.05. Проверяем каждый seed;
не выбираем лучший результат. Пороговые значения фиксированы в QualityPolicy,
они не подстраиваются автоматически под текущие ошибки.

Для изменений архитектуры backend, autograd, loss, оптимизаторов и sampling
сохраняем успешный report.json как baseline, затем сравниваем новый прогон:

```powershell
& '.\.venv\Scripts\python.exe' scripts/benchmark_solutions.py --output-dir numerical-reports\standard-002 --baseline numerical-reports\standard-001\report.json
```

Нужны одинаковые задачи, seeds, бюджеты, PDE-файлы, конфиги и сетки. При изменении
контракта бенчмарка создаём новый baseline явно. Изменение production-кода
разрешено: именно его влияние мы измеряем. Сравнение проверяет absolute quality
и ухудшение relative L2, max_error и PDE RMSE более чем в 1.5 раза плюс небольшой
абсолютный запас (0.002, 0.005 и 0.005). У почти нулевых ошибок этот запас защищает
от ложных тревог округления. Это практический регрессионный порог, не
статистический тест значимости; для спорных изменений расширяем набор seeds.

Несовместимый baseline отклоняется до обучения, чтобы не расходовать GPU-время.
В summary отчёта сохраняются медиана, минимум и максимум общей L2 по seeds.

Сохраняем полный отчёт с Git SHA, версиями Python/Torch/Lightning, GPU и метриками
каждого seed; отдельные result.json, конфиги, логи, MAT и checkpoints остаются в
каталоге запуска. В отчёте виден признак dirty working tree; для сравнения кода
предпочтительны чистые commits. Git SHA сам по себе не описывает незакоммиченные
изменения. Время сравниваем на одинаковом оборудовании, не Mac против RTX.

Команда возвращает 0 при успешной приёмке (либо успешном smoke), 1 при падении
runner, порога качества или регрессии. Неверные параметры/CUDA-недоступность
возвращают argparse-код 2. Скрипт никогда не переключает CUDA на CPU сам.

## Когда запускать

Быстрые math/metric-тесты входят в обычный check.py. Smoke public runner — e2e.
Долгие CUDA-прогоны запускаем при завершении крупных изменений обучения и перед
выпуском. Не запускаем заново из-за документации или переименований. Если
изменилась только одна PDE-ветка, сначала проверяем её, затем весь набор на
завершении блока. Прежний check_backend.py остаётся быстрой проверкой устройств
и переноса checkpoints; новые бенчмарки проверяют численное качество.

## Время и пропускная способность

Каждый trial теперь содержит отдельный объект `performance`:

- `training_seconds`, `training_steps_per_second`: время всего train-процесса и
  число optimizer steps / это время. Включает запуск Python, подготовку,
  обучение, checkpoints и завершение; это эффективная скорость файлового runner.
- `prediction_seconds`, `prediction_points_per_second`: время всего predict-
  процесса и число пространственно-временных точек / это время. Включает импорт,
  загрузку весов, подготовку сетки, перенос данных, Lightning и запись MAT.
- `warm_prediction_seconds`, `warm_prediction_points_per_second`: время прохода
  всей той же сетки через `predict_step`, когда модель и входы уже на устройстве.
  Включает батчирование Python и вычисления модели, исключает загрузку весов,
  Lightning loop, перенос CPU↔GPU и запись файлов. CUDA синхронизируется перед
  и после прохода, иначе секундомер измерял бы постановку kernels в очередь.
- Три прогревочных прохода и семь измерительных; сохраняем медиану, минимум,
  максимум, число точек и batch_size. На heat2d это 52 111 точек; в 1D — 1271.

В `summary.performance_median` — медианы по seeds. Не смешивайте полное время
файлового запуска с временем прогретой сети. Для одноразового контейнера важно
первое, для исследования вычислительного backend — второе. Время не является
автоматическим порогом падения: фоновые процессы и тактовая частота GPU могут
меняться; численные пороги качества остаются независимыми.

Если модели уже обучены, можно добавить измерения predict и повторно проверить
ошибку, не расходуя время на новое обучение:

```powershell
& '.\.venv\Scripts\python.exe' scripts/benchmark_solutions.py --output-dir numerical-reports\timing-new --measure-existing numerical-reports\standard-001 --baseline benchmarks\baselines\rtx4070ti-standard.json
```

Проверяются fingerprint, steps и неизменность functions.py. Время обучения
переносится из исходного result.json, а инференс измеряется заново. Отчёт явно
содержит `training_origin` (каталог и commit обучения), а trial —
`training_reused_from`; новый inference не выдаётся за новый train. Обычный запуск
без `--measure-existing` измеряет оба процесса заново.

Фактическое измерение `timing-001`, commit `5384199`, RTX 4070 Ti, batch=2048,
float32 matmul precision=`highest`, TF32 выключен; медианы двух seeds:

| Задача | Train-процесс | Шагов/с | Predict-процесс | Прогретая сеть (вся сетка) | Точек/с, прогретая сеть |
|---|---|---|---|---|---|
| heat2d | 25.18 с | 119.2 | 2.290 с | 7.102 мс / 52 111 точек | 7.36 млн |
| advection | 17.41 с | 172.4 | 2.232 с | 0.274 мс / 1271 точка | 4.64 млн |
| burgers | 22.79 с | 131.6 | 2.226 с | 0.264 мс / 1271 точка | 4.82 млн |

Время train взято из `standard-001`; новый train в этом прогоне не выполнялся.
Predict и прогретая сеть измерены заново. Разница полного predict и прямого
вычисления сети существенна: для короткого одноразового запуска время подготовки
и обвязки нельзя игнорировать. В измерения сети не включена невязка PDE.

Проверки разработки: полный Mac-набор 186 тестов до CLI-исправления; полный

### Временная диагностика

Каждый trial содержит temporal_metrics (RMSE, L2, max, boundary/interior RMSE
на каждом времени) и diagnostics: worst_time_l2/worst_time, undefined_layers,
pde_time_bins, holdout_seed/points/version. Нулевой reference norm обозначается
null и учитывается в undefined_layers, без искусственного epsilon.

PDE residual агрегируется по 10 равным временным интервалам на прежних 2048
holdout-точках seed 20261013. Интервалы слева включительные и справа исключительные;
конечное время входит в последний. Пустой bin имеет points=0 и null ошибки.
Это диагностические поля, пока не новые quality gates. Они не участвуют в loss,
не меняют веса и не меняют training fingerprint. --measure-existing позволяет
получить их для прежних checkpoint без повторного обучения.

Эксперимент с весом BC запускается флагами --boundary-weight 1/3/10 и
--gradient-norm-every 200. Каждая комбинация использует отдельный output-dir.
BenchmarkVariant применяет TrainingAdapter к конфигу исходной задачи: PDE,
аналитический эталон, границы и оценочная сетка не меняются. Fingerprint учитывает
recipe; baseline сравнение разных recipe пока намеренно запрещено. Для абляций
сравниваем отдельные отчёты при одинаковых seeds/бюджетах.


## Полиномиальный контроль Неймана

Добавлены выбираемые явно `heat_neumann_polynomial1d/2d/3d`:
нулевые нормальные производные, полиномиальное начальное поле и известный
источник. Аналитический ответ служит только проверке. Это контроль будущих
преобразований, которые могут незаметно ограничить третьи граничные производные;
[формулы и предпосылки](polynomial-neumann-control.md).
Общий набор по умолчанию остался прежним.

Режим со срезами теперь запускает каждый опыт в отдельном процессе и отдельно
измеряет обученный исполнитель и независимый контроль:
[время до точности и схема 3](time-to-quality-screening.md).

## Проверка самого граничного условия

В новых отчётах явно разделены `boundary_temperature_rmse` и ошибки физических
операторов по каждой грани. Прежний `boundary_rmse` сохраняет смысл ошибки
температуры, в том числе у Неймана/Робина. Ни критерий текущей серии, ни старые
данные не переименовываются задним числом. Формулы, точки проверки и единицы:
[граничные метрики](boundary-error-metrics.md).
